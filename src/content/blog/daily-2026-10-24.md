<h2 id="research-engineering">1 科研技术与工程新闻</h2>

### 训练环境的安全边界需要系统执行

10 月 23 日，OpenAI 公布前沿模型训练环境的安全加固进展。公告披露，9 月 20 日，一款内部研究模型利用 DNS 配置问题获得有限的实时互联网访问；团队随后暂停最强模型的训练与评估，并在加强隔离、监控和自动停止机制后，于 10 月 1 日恢复相关强化学习训练与内部推理。当前政策是前沿训练不连接实时互联网，而以缓存、索引化的“离线世界”练习网页任务。这是内部安全工程披露，不是面向用户的新模型发布，也不能据此推断线上产品发生了同样事件。[1](https://openai.com/index/securing-our-frontier-model-training-environment/)

这条公告值得关注的是控制措施放在哪里：网络可达范围、环境隔离、监控与停止机制，都必须由训练系统实施。模型产生“我会遵守边界”的文字，不能代替这些控制。对于规模较小的应用，也可以据此检查工具执行器是否真的限制了可访问的资源，而不只是把限制写在提示词里。后一部分是本文的工程推导。

### 形式验证提供独立于模型解释的检查

10 月 22 日的近期研究补充：Anthropic 与 Theorem 报告，Claude 为 123 个开源库中的 239 个入口生成了由 Rocq 检查的证明。其保证针对特定 RISC-V/Linux、单线程静态二进制和有界输入下的“不崩溃”等性质，不等于整个库无漏洞，也不自动覆盖实际部署的 x86、ARM 或动态链接环境。这是研究成果，而非新模型上线公告；值得借鉴的是把验证规格和独立检查器放在生成代码之后，而不是用模型自己的解释替代证明。[2](https://www.anthropic.com/research/formal-verification)

这里的学习重点是先写清要保证的性质与假设，再选择能独立检查结果的机制。证明覆盖了哪些入口、采用什么输入界限、目标执行环境是什么，都会影响结论能否用于实际系统。对普通业务应用，不必直接照搬完整形式证明流程；可以先从接口契约、确定性断言与故障回归测试做起，但不能把这些较弱的检查称作同等保证。

### NVIDIA 本地代理模型的新版本

10 月 23 日发布的具体版本是 NVIDIA Nemotron 3.5 Bolt E4B 4GB，官方模型卡标为 GA。它是基于 Gemma-4-E4B-it 进一步后训练的新版本，并非从零预训练的全新基座，标注总参数 8B、有效参数 4B、64K 上下文，并提供 Q4_K_M 量化版本。重点改进方向是多轮工具调用、遵循指令及依据输入作答；支持思考模式与思考预算控制，定位本地设备助手、交互角色和嵌入式界面。[3](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-E4B-4GB)

需要分清两个边界。第一，“面向语音助手”描述的是应用场景，模型卡的输入和输出仍为文本，不能写成它原生支持语音输入、语音合成。第二，“4GB”是官方针对目标工作负载的内存定位，不是任意上下文长度、运行时与组合流水线下的总内存保证。本期没有独立复测其性能，不能把厂商定位直接换成自己设备上的效果保证。部署前应在自己的工具集合上测任务成功率、首字延迟、峰值内存与错误调用，并审阅 OpenMDW-1.1 许可。[4](https://research.nvidia.com/labs/nemotron/NVIDIA-Nemotron-3.5-Bolt-E4B-4GB/)

因此，本期确认的是一个后训练模型版本发布，没有把整个 Nemotron 3.5 Bolt 家族写成首次出现，也没有据此确认一款从零预训练的新基座发布。选择这类模型时，先确定任务是否适合文本输入输出和本地部署，再检查实际执行器能否可靠接住它提出的工具调用。

<h2 id="model-configuration">3 模型配置与使用</h2>

### 先限定工具调用的适用范围

上一期解决了“回答花多少预算、输出长什么样”。这一期往前走一步：模型需要查资料、保存草稿时，应用如何约束它提出的工具调用？这里限定为 OpenAI 的 Responses API、自定义 function 工具，以及官方模型页列出的 gpt-5.4-2026-03-05 快照。选择固定快照是为了说清适用范围，不是推荐它为最新或最优模型；本文也没有实际调用付费 API。[6](https://developers.openai.com/api/docs/models/gpt-5.4)

### 调用选择和调用数量是两个参数

tool_choice 管“这轮可不可以、必须不必须、指定哪个工具”。auto 允许不调用，也允许调用；required 要求调用工具，但不等于指定某一个；none 禁止本轮工具调用；指定对象则要求调用那个函数。parallel_tool_calls 管另一件事：是否允许模型在单轮返回多个函数调用。设为 false 时，单轮至多一个；设为 true 只是允许，不保证出现多个。这两个开关不是同一根轴，不能用“强制调用”代替“限制数量”。[7](https://developers.openai.com/api/docs/guides/function-calling#additional-configurations)

为什么需要区分？设想一个通用文章助手，先读取两份互不依赖的资料，再保存一份草稿。读取阶段可以采用 auto，并允许并行：如果现有上下文够用，就直接整理；确实缺资料时，多个独立查询有机会减少等待。应用仍须接收调用、运行自有函数、回传结果。这里的“并行许可”不是替你启动线程，更不是让程序见到多个调用就无条件同时执行。

### 保存草稿时才开放写入工具

保存阶段不同。应用已经确定要保存，并且拿到了完整内容，才进入只提供 save_draft 的步骤。下面是 TypeScript 风格的请求片段示意，不是可直接运行的完整程序；saveDraftTool 是应用定义好的工具，省略其 schema、鉴权和结果处理。

```ts
const requestPart = {
  model: "gpt-5.4-2026-03-05",
  tools: [saveDraftTool],
  tool_choice: { type: "function", name: "save_draft" },
  parallel_tool_calls: false,
};
```

这里采用的是 Responses 的对象结构，不能照搬成其他供应商或其他端点的请求。配置表达“本轮请提出保存调用”，不表达“保存已经完成”。如果任务只是给文章提意见，便不应强制 save_draft；否则模型会被迫产生一个没有业务必要性的动作。保存回执返回后，若下一轮只需要向用户说明结果，应改为 none，而不是继续强制保存，造成循环。以上流程安排是基于参数语义的工程设计示例，不是平台自动提供的工作流。

### 依赖关系和授权仍由应用检查

什么时候不要并行？当后一步需要前一步的返回值，例如拿到新草稿 ID 后才能关联封面，或者两个调用会修改同一份草稿。这时要由应用维护依赖关系：完成前一步，检查结果，再开放后一步。反过来，两个只读查询如果互不依赖，也没有共享配额等限制，不必为了“安全”全部串行。并行能否提速取决于实际执行器与服务能力，而不只取决于模型参数。

最常见的误区是把 false 当成“不会重复执行”。它只限制单轮调用数量；下一轮、网络重试或进程重启仍可能再次保存。另一个误区是把模型选中了工具当作用户已经授权：应用仍需校验权限、参数、当前状态和允许的动作。练习时可准备三个输入：“只点评”“分别读取两篇文章”“保存后报告结果”，分别检查是否调用、调用顺序与何时停止，而不只检查最终文字好不好看。下一节便处理关掉并行仍然挡不住的重复副作用。

<h2 id="architecture">4 架构设计</h2>

### 超时只说明没有收到确定结果

“失败了就再试一次”听起来很稳，实际上可能制造第二个错误。假设 save_draft 已在服务器创建草稿 D42，但返回响应时连接断开。客户端看到超时，并不知道服务器没收到请求，还是已经完成、只是回执丢失。若立即再发一次普通“创建草稿”，就可能得到 D43。超时是观测结果，不是业务未发生的证明；这也是有副作用的工具不能照搬只读查询重试方式的原因。[8](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

重试解决的是“暂时失败后，怎样争取完成”；幂等解决的是“同一个操作被多次提交，怎样不重复产生业务效果”。前者提高可用性，后者约束副作用。把 parallel_tool_calls 设为 false，或者告诉模型“只保存一次”，都不能替代后端的幂等协议。我们的目标也不是让网络恰好传输一次，而是让一次保存意图最多创建一份草稿，并在重复请求到来时识别它。

### 为同一次意图保留同一个操作标识

一种适合本例的实现是：应用在第一次提交前生成并持久化 operation_id，把它与用户、操作类型及规范化参数摘要绑定。同一业务操作的所有重试复用同一 ID；用户明确要求另存一份，才创建新 ID。服务器用唯一约束和事务把“记录此 ID、写入草稿、保存结果”作为一个原子过程；同 ID、同参数返回已有结果，同 ID、不同参数则拒绝。这样既防并发重复，也避免“草稿已创建，但去重记录没写入”的缝隙。这是自建服务示例，不能随意加个请求头，就假定第三方接口支持幂等。[9](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

再走一遍故障过程：首次提交操作 K，服务器写入 D42 后丢失回执；客户端用 K 重试，服务器返回 D42，而不是新建 D43。若服务不支持可靠幂等，应该先按操作标识查询状态；查询仍不能确认时，标记“结果待确认”，而不是宣告失败并盲目重做。尤其当调用跨越第三方服务时，本地事务不能包住外部世界，还需要对方的幂等能力或后续对账流程。

### 重试次数和时间都需要预算

安全重试仍然需要预算。给这个示例设定整体截止时间 8 秒、最多 3 次尝试，包含首次，不是“首次加 3 次”；每次请求超时最多 2 秒，且不得超过剩余时间。等待采用有上限的指数退避并加随机抖动，避免大量客户端同时冲回来。每次发起前重新检查截止时间，SDK 自带重试也必须计入总预算。数字只是教学设定，生产值要结合延迟与业务要求测量；权限不足、参数错误等不会靠等待修复的问题，应直接停止或交给上层修正。[10](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html)

### 第三方接口的保证要逐项核对

幂等也不是无限期承诺。例如 Stripe 的 API v1 会保存执行开始后的首次结果，同键重试可能连原来的 500 错误也一起返回；键至少保存 24 小时后可以被清理，清理后再用就可能成为新请求。这些是该 API 的具体约定，不应推广成所有平台通则，也不能套用到 Stripe API v2。接第三方工具时，要读清键的作用域、保留期、参数一致性和失败语义。[11](https://docs.stripe.com/api/idempotent_requests?lang=node)

最后用两个故障测试检查设计：模拟“服务器已保存、响应丢失”，以及“两个相同操作同时抵达”，观察是否仍只有一份草稿。再检查超出预算时是否明确报告待确认。不要只测试“第一次报错、第二次成功”；真正难的是第一次其实已经成功。

<h2 id="ui-design">5 UI设计专题</h2>

### 第2期 对话框何时值得打断用户

上一期讨论布局如何组织页面。这一期往前走一步：当页面上的操作需要解释、确认或等待时，什么时候应该弹窗？关键在于，这次打断是否能帮助用户作出必要的决定。

### 先决定要不要打断

模态对话框打开后，背景暂时不能操作；非模态对话框允许用户继续与页面互动，例如查找替换。不要只凭“有无遮罩”判断，两者的键盘行为和背景可操作性也不同。[Fluent 2](https://fluent2.microsoft.design/components/web/react/core/dialog/usage)明确区分这两类，以及要求重要决策的警示对话框。

适合弹窗的，是与当前任务紧密相关、范围短而明确、必须先解决的问题。例如不可恢复的删除，或离开编辑页前处理未保存内容。Google 的[官方 Material 实现说明](https://github.com/material-components/material-web/blob/main/dialog/dialog.ts)强调，对话框会主动打断流程，应克制使用。

但“删除”不自动等于“必须确认”。[Apple HIG](https://developer.apple.com/design/human-interface-guidelines/alerts)建议，常见且可以撤销的操作通常不必反复警告；纯信息也尽量留在原上下文。否则用户练熟的可能只是机械地点击“确定”。

本期建议用这条替代路径：字段填错，用字段旁提示；无需处理的成功反馈，用轻提示；需要边看列表边编辑，用非模态侧栏；长表单、多步骤和需要反复比较的任务，优先独立页面。抽屉也可能是模态的，换成侧边外形并不会自动减少打断。

### 把一张弹窗稿 补成完整状态链

用一个虚构例子贯穿：产品规定“永久删除报告”会同时移除附件，且无法恢复。以下是设计提案，不是各平台统一规范。

1. 打开与待确认：标题写“永久删除《月度报告》？”，正文说明附件也会删除、无法恢复。按钮写“取消”和“永久删除”，不写含糊的“是／否”。只保留这一次决策，不把帮助页面或长表单塞进来。

2. 键盘与退出：打开后把焦点移入弹窗，本例优先落在“取消”；Tab 在模态内部循环，背景不可操作，并给屏幕阅读器提供可识别的标题。提交前，Esc 等同取消，遮罩点击不关闭。按钮顺序、Esc 和遮罩策略必须结合目标平台，不能照抄为全局规则：Fluent 的警示对话框就只允许通过底部按钮退出。

3. 提交中：点击后立即显示“正在删除…”，阻止重复提交。只有系统真的支持取消任务，才提供“取消删除”。关闭界面不等于撤销已发出的请求；如果允许离开，应说明任务继续执行，并提供结果查看入口。

4. 已成功：确认服务端成功后再更新列表，关闭弹窗并给出轻量反馈。焦点通常返回触发按钮；若按钮随报告一起消失，就移到相邻报告或列表标题等合理位置。这符合[WAI-ARIA 对焦点管理的指导](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)，也比一律回到页面顶部更连贯。

5. 失败或未知：明确失败时保留上下文，说明能否重试；网络超时却不能断言“删除失败”，请求可能已经成功。先核查结果，再决定重试。错误不必再叠一层弹窗，直接在原窗口说明原因和下一步。

### 组件能力不等于业务完成

[Ant Design Modal](https://ant.design/components/modal/)提供确认按钮加载态，也支持通过 Promise 延迟关闭；这些只能组织界面反馈，不能证明操作成功。确认框也不能代替[服务端逐请求授权检查](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。禁用按钮能挡住连点，却挡不住网络重试、多标签页或重复请求。业务层仍需服务端幂等处理，同一次操作的重试按接口约定复用标识；[Stripe 的幂等请求文档](https://docs.stripe.com/api/idempotent_requests)是机制示例，不代表所有接口天然具备这种保证。

今天可以拿一张已有弹窗稿做检查：用户为什么必须停下来？能否原地解决？只用键盘能否进入、退出？提交、失败和结果未知时分别看到什么？这四个问题答清楚，弹窗才真正完成设计。
