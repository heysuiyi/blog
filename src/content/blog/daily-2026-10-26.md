## 3 模型配置与使用

### 提示词缓存：复用的是输入前缀，不是答案

同一本操作手册被连续问十遍，是否必须十次都按普通输入价格处理？本节讨论 Claude API 的提示词缓存，并限定模型为 `claude-sonnet-4-6`；官方目前将它列为仍可用的 legacy 模型，选择它只是固定教学边界，不代表推荐新项目优先采用。不要把本节字段直接搬到 OpenAI Responses API。[模型与版本](https://platform.claude.com/docs/en/models/sonnet-4-6/overview)

先想象一家虚构设备服务商：客服每次都附上相同的产品手册与回答规范，随后追加不同工单。如果把“当前时间、工单编号、客户姓名”插在手册前面，重复资料虽然很多，请求开头却已经改变。缓存需要稳定前缀，而不是“内容大致相似”；官方诊断文档特别列出了时间戳、工具顺序和早期消息修改造成的失配。因此，设计时先把提示拆成稳定资料与动态问题两层，并固定资料版本和序列化方式。[前缀变化与诊断](https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics)

在 Claude 的内容块上设置 `cache_control: {"type":"ephemeral"}`，可以显式标记缓存边界；本例放在完整手册所在块的末尾，工单另放后面。Sonnet 4.6 的最低可缓存长度为 1,024 tokens，不是 1,024 汉字。默认缓存期限为五分钟，也可设置 `ttl:"1h"`；命中会刷新期限，计时从相应写入或读取请求开始。不要把超过所选期限当作必然未命中，仍以实际计量确认。验收看响应 `usage`：`cache_creation_input_tokens` 表示写入量，`cache_read_input_tokens` 表示读取量，`input_tokens` 是剩余普通输入；三者相加才是总输入。[缓存配置与计量](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

成本要算完整一轮，不能只看命中时的折扣。该模型标准价每百万 tokens：普通输入 3 美元，五分钟缓存写入 3.75 美元，一小时写入 6 美元，缓存读取 0.30 美元。[官方价格](https://platform.claude.com/docs/en/about-claude/pricing) 据此自行计算：假设可复用前缀恰好一万 tokens，第一次写入、第二次全部命中，五分钟方案的前缀费用为 0.0405 美元，普通输入两次为 0.06 美元；一小时方案两次则为 0.063 美元，尚未更便宜。这里只比较前缀，排除了输出、动态输入与其他收费项，也没有假设每次都命中。

所以，“更长期限更省钱”是误区。适合开启的是资料较长、版本稳定、短时间反复使用的工作流；不适合优先折腾的是偶发短问答、每次资料完全不同的任务。更不应该为凑门槛塞无关文字，或为了保持命中而继续使用过期政策。缓存不是答案数据库，不能拿命中率代替回答质量检查。

今天的练习：准备一份足够长的虚构手册，先写出四行测试计划——首次请求、仅改末尾问题、修改手册首段、隔开超过所选期限再请求。运行时保持模型与其他参数固定，逐次记录三项输入计数、输出量、耗时及估算费用；先等首次响应开始，再发送后续请求。预期不是“四次都命中”，而是能解释每一次读取或重建，并用真实计量判断是否值得保留配置。没有 API 条件也可先完成请求分层与费用表，不要把预期写成实测结果。

*核验：2026-10-26，北京时间。以上链接为官方当前文档，不将核验日期当成发布日期；本节未实际调用 API。*

## 4 架构设计

### 人工审核中断与恢复：批准必须绑定具体版本

昨天解决的是“任务停下以后，状态放在哪里”；今天解决“人点过同意，究竟允许执行哪一件事”。两者不同：存下状态不等于获得授权，能够恢复也不等于应该执行。人工审核的核心不是界面上多一个按钮，而是让待审内容、审批记录和最终执行保持一致。

LangGraph JavaScript 提供 `interrupt()` 暂停节点，再用相同 `thread_id` 和 `new Command({ resume: ... })` 恢复；需要配置 checkpointer，生产环境应使用持久化实现。尤其要注意：恢复时节点从开头重新运行，并非跳回暂停位置继续执行。因此，把外部写操作放在中断之前，会引入重复执行风险。[官方中断语义](https://docs.langchain.com/oss/javascript/langgraph/interrupts) 这些是框架机制；下面的版本绑定、权限检查和审批失效策略，是本例需要自行实现的应用设计。

假设一个虚构运营助手准备发送供应商通知。待审包不能只有“是否发送”，而应展示发件身份、全部收件人、标题、正文、附件版本及发送范围。应用保存一份不可变的待审快照，生成 `action_id`、版本号和内容摘要。审核人批准的是“通知 A 的第 3 版”，不是以后任何叫作 A 的通知。若模型随后把附件换成新版，即使正文一字没动，也应生成第 4 版，使旧批准不能直接用于新内容。

一个清晰的流程是：生成候选动作，冻结待审快照，等待审核，服务端校验，最后执行。恢复接口收到“批准”后，先验证登录者身份和审批权限，再检查动作仍处于待审状态、版本与摘要一致、审批没有过期或撤销。执行节点应读取获批快照，而不是重新请模型生成正文，也不能读取一份仍可被编辑的“最新草稿”。如果任何检查失败，回到待审或拒绝状态，而不是让模型解释一下后继续。

还要处理“检查通过后，内容恰好被改了”的时间差。可以用数据库条件更新，把“当前版本仍等于获批版本且状态仍为待审”作为领取执行权的条件；更新成功才执行被冻结的快照。第二个审核者晚到的批准、浏览器双击或旧页面回传，都不能再次领取同一动作。这里的重点是授权对象不漂移，而不是展开另一套重试教程。

哪些地方值得加这道关？对外发送、敏感权限变更、难以撤销的批量写入，是候选场景；本地格式检查、可丢弃草稿生成等低风险步骤，不必每一步打断人。也不要把“编辑”自动当作“已批准”。LangChain 的工具审核中间件确实区分批准、编辑与拒绝等决策，但是否要求修改后再次审核，是应用必须明确的策略，不是框架替你决定的业务规则。[工具审核决策](https://docs.langchain.com/oss/javascript/langchain/human-in-the-loop)

今天的练习不需要真实邮箱：把发送工具换成仅追加到本地数组的模拟函数。准备三个测试：第 3 版获批后，执行记录必须与第 3 版完全一致；审核人打开第 3 版后修改收件人，再从旧页面提交第 3 版批准，必须被拒绝；重复提交同一批准，模拟发送次数仍只能为一。再加一个无权限审核者，确认仅知道 `thread_id` 不能获得执行权。验收标准不是“流程成功跑完”，而是错误批准和过期批准也确实无法越过边界。

*核验：2026-10-26，北京时间。采用官方 JavaScript 中断基本接口，不依赖新增响应 schema 功能；在线文档没有统一锁定包版本，落地时应按项目实际版本核对接口。未运行 SDK 或外部发送。*

## 5 大厂UI设计

### 表单让人少填错

表单是把人的意图变成可处理信息的一组控件。设计它之前，先问每个字段是否真的必要。以下用一个虚构的工作坊报名页推演：组织者需要姓名和接收通知的邮箱，却未必需要公司、职位与手机号。删掉无用途的问题，既缩短填写过程，也减少出错机会。需要创建记录、预约或提交申请时，表单很合适；只为浏览活动介绍，就不应先要求用户交出一整套资料。

字段里最容易混淆的是标签和占位提示。标签回答“这里填什么”，应让人输入之后仍能确认；placeholder 可以提供示例，但会随输入消失。报名页可以保留“接收通知的邮箱”标签，在输入框内放“例如 name@example.com”，把“用于发送入场信息”放在旁边。不要把用途、格式和必填要求全塞进一行灰字。Apple HIG 也指出，占位文字消失后，独立标签有助于提醒字段用途；这并不等于所有原生界面都必须照搬同一种标签布局。[Apple HIG：Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields)

必填与选填要提前讲清。假如报名只需姓名和邮箱，备注可以直接标“备注（选填）”；若采用星号，则应解释含义，并保持一致。不要用一个红色星号同时表示“必填”和“已出错”。Ant Design 的 `requiredMark` 支持配置必填或选填标记，实际校验规则仍要另外正确配置：样式上的星号不能代替规则。[Ant Design：Form](https://ant.design/components/form/)

提示也应该出现在用户作决定之前。假设工作坊允许填写希望讨论的问题，页面可以先说明“请描述一个最想解决的问题”，而非等提交后才宣布长度限制。明确、有限的选项宜让人选择；真正开放的回答才需要文本输入。若只收姓名，却放一个巨大的多行框，用户可能误以为需要自我介绍。控件本身就在传达你期待什么答案。

校验时机则要看字段。邮箱刚输入第一个字母时就报错，只会制造噪声；在这个例子中，可以等用户离开字段后再检查格式，提交时再做完整检查。需要边写边理解的密码规则，则可以及时反馈。Apple HIG 明确区分了邮箱与用户名、密码的校验情境。Ant Design 提供 `validateTrigger` 和 `validateDebounce` 等配置；它的默认行为是实现起点，不是所有产品都该遵守的统一规范。[Apple HIG：Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields) · [Ant Design：Form](https://ant.design/components/form/)

发现问题时，要告诉人怎么修。把“输入非法”改成“邮箱似乎缺少 @，请检查地址”，并保留已填写的姓名与备注。假如地址格式正确但通知服务暂时不可用，就不要把邮箱标成用户填错。提交按钮可写“确认报名”；请求处理中说明“正在提交”，避免重复操作，只有收到成功结果才宣布完成。这里的重点是让填写动作有可信的结尾，而不是把所有异常都压成一句“提交失败”。

最后，用键盘和读屏走一遍真实流程。Web 表单的标签需要与控件在代码中关联；错误也应有文字说明，并可通过 `aria-describedby` 关联字段，不能只靠红色描边。W3C 的表单教程分别说明了这些做法。[W3C：Labeling Controls](https://www.w3.org/WAI/tutorials/forms/labels/) · [W3C：User Notifications](https://www.w3.org/WAI/tutorials/forms/notifications/) 移动端则应按内容选择合适键盘，并检查“下一项”是否顺畅；Apple 平台还有各自的输入习惯。[Apple HIG：Text fields](https://developer.apple.com/design/human-interface-guidelines/text-fields) 一份好表单，不需要用户先记住规则、再凭记忆闯关：问题清楚、要求提前、修正有路，才是真正减少填错。

来源与版本：Ant 6.6.7、Apple 在线 HIG（非固定版本）、W3C 文档均于 2026-10-26 北京时间核验；Apple 正文经官方索引核读，直接打开受 JS 限制；案例为推演，未运行组件测试。


## 今日实践

选一个测试环境中的文档审批表单：先给固定资料标版本，把可缓存的前缀与动态输入分开；再让审批绑定标题、正文与附件的同一份快照；最后故意改一个必填字段，观察错误是否说明修正办法并保留其他内容。只需先画出流程和四条验收记录，不必立刻接真实API。

重点留下四种观察：相同资料再次请求是否真的命中缓存，修改资料后是否重新计量，修改待审内容后旧批准是否失效，以及输入错误能否在原处修正。成本节省、授权正确和操作顺畅要分别验证，不能用其中一项替代其他项。

下一期配置继续讨论模型输出结束原因与截断处理；架构转向工具返回结果的校验；UI连载进入信息层级，讨论重要内容如何被看见。这些是连载方向，不预设届时一定出现新模型新闻。
