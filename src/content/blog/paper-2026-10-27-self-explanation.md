一段代码只有十来行，你能说出每行在做什么，跟着讲解也算出了正确答案。过了一会儿，有人把其中的“大于等于”改成“大于”，问程序还能不能完成原来的任务。你又得从头猜。

本文讨论的就是这个缺口：读懂字面操作以后，怎样检查自己是否知道这一步为什么成立。我们会借一项自我解释研究提出问题，再用一个完整的小例子练习。这里不评判谁聪明，也不要求把每行代码讲成长篇。重点是把条件和结论之间缺失的理由写出来，并允许证据推翻它。

学习还有另一个问题：换了情境，能不能主动想到学过的方法，那属于迁移的检查。本文先把镜头拉近，检查同一道题内部的推理。即使你没有读过本系列前文，也可以直接从下面的例子开始。

## 论文提供的线索和证据边界

Chi 等人1994年正式发表于《Cognitive Science》的研究，让24名自愿参加的八年级学生学习人类循环系统。14人逐句解释，并接受22处功能提问及必要的澄清追问；10人将材料读两遍。论文未报告随机分组。至少一周后的后测允许查阅材料与笔记。两组总体成绩分别增加约32和22个百分点，不能写成“提高32%和22%”。

实际平均学习时间为125和66分钟，并不等时。因此，差异不能全归于解释本身，也不能据此断言成人编程学习已经得到验证。研究把超出原句的信息推论计作自我解释，换词复述不算在内。［原刊 pp.450–456；链接见文末］

以下代码、提问和练习均为本文原创的教学示例，并非论文实验材料，也没有单独验证过其教学效果。我们只借这个区分，观察自己究竟补出了什么理由。

## 先把要完成的任务说清楚

假设有一个已经按从小到大排列、允许重复的整数数组：

```text
位置：  0  1  2  3   4
数值： [2, 5, 5, 9, 13]
```

给定目标值 `x = 5`，我们想找到第一个大于或等于它的数的位置。答案是 `1`，不是 `2`，因为两个 `5` 都满足条件，但前一个更早。位置从零开始计数；若所有数都比目标小，就返回数组长度，表示没有这样的元素。

下面这段 Python 代码完成这个任务。暂时不熟悉二分查找也没关系，只需知道它每次查看中间位置，再缩小答案可能所在的范围。

```python
def first_at_least(a, x):
    left, right = 0, len(a)
    while left < right:
        mid = (left + right) // 2
        if a[mid] >= x:
            right = mid
        else:
            left = mid + 1
    return left

assert first_at_least([2, 5, 5, 9, 13], 5) == 1
```

看见 `right = mid`，你可能说：“如果中间的数大于等于目标，就把右边界移到中间。”这句话准确描述了操作，可以帮助刚接触语法的人读代码。但它还没回答为什么这样移动不会漏掉答案。

另一种常见说法是：“因为二分查找每次要缩小一半。”它描述了大致做法，却不能决定该保留哪一边。错误的代码同样可以很快缩小范围。因此，先别急着解释效率，先解释删掉的那些位置为什么不再需要考虑。

## 把一步操作还原成一段推理

对 `right = mid`，可以试着写出这样的理由：

“当前位置的数已经满足要求，所以最早满足要求的位置不可能在它右边。但左边可能还有满足要求的数，我不能马上返回当前位置。接下来把答案位置的上限收紧到 `mid`，仍然允许 `mid` 自己成为最后答案。”

这里的每句话都有工作要做。“满足要求”来自当前比较；“最早”来自题目目标；“不能马上返回”说明为什么还要继续找；最后一句解释边界更新时为什么不能把当前候选一起丢掉。

注意，`right` 在这段代码里是一个边界。赋值后，不必再去检查位置 `mid` 的元素，但答案仍可能等于这个边界。把“还要检查哪些元素”和“最终答案可能是哪个位置”混为一谈，容易给正确代码配上一段错误理由。

再看另一个分支。若 `a[mid] < x`，为什么可以令 `left = mid + 1`？这里必须用上数组有序：当前位置都还太小，它左边的数只会更小或相等，所以这些位置都不符合要求。答案只能在其右边。若解释中漏掉“已经排序”，就缺了允许整段排除的依据。

你可以把两段推理压成一句持续检查的话：左边界之前的数都已确认太小；右边界若对应真实元素，它及其右边都已满足要求。答案位置始终落在两个边界之间，包括边界本身。每次更新都要保住这件事，两个边界相遇时，留下的才是所求位置。

不一定要背下这句话。更有用的做法是拿纸走一遍：起初 `left = 0`、`right = 5`，中间位置是 `2`，值为 `5`，于是右边界变为 `2`；接着中间位置为 `1`，仍是 `5`，右边界变为 `1`；最后中间位置为 `0`，值为 `2`，左边界变为 `1`。两边相遇，返回 `1`。

每走一步都问：这次排除的是什么，凭什么排除？这样记录，比只写三个中间数更能暴露缺口。

如果脑中只有“这是标准写法”，可以暂时保留这句话，再追问它依靠什么。题目要求最早的位置，是需求给的；数组有序，是输入给的；当前位置符合条件，是比较得到的。把来源分开以后，容易发现哪些是已有事实，哪些只是自己顺手加上的假设。你不必一次写出完整证明，但至少要知道下一条需要核对的依据在哪里。

也不用每次都从头讲完整个程序。变量赋值已经熟悉，就先跳过；优先停在会改变结果的选择上，比如这里为什么保留当前位置，另一个分支为什么跳过当前位置。等这两个问题说清楚，再问循环为什么会结束，找不到时为什么返回长度。解释应当跟着疑点走，不能只用字数衡量是否认真。

## 解释写出来以后要试着推翻它

解释很流畅，也可能错。假如你写的是“发现相等就已经找到答案”，用刚才的重复值就能检查：第一次命中位置 `2`，若立即返回，会错过位置 `1`。你需要修改的不是措辞，而是对任务的理解：我们要找最早的位置，不能只找到一个匹配值就停。

回到开头的问题，把 `>=` 改成 `>`，相等的元素就会被当作不合格而排除。对 `[2, 5, 5, 9, 13]` 和目标 `5`，程序将返回位置 `3`，找到的是第一个严格大于目标的数。一次符号改动改变了任务含义，这正是需要说明理由的地方。

再假如你写的是“中间的值小，就能丢掉左边”。把数组换成 `[9, 2, 5]`，目标仍为 `5`。程序先看到中间的 `2`，排除左侧，最终返回 `2`；但按“第一个大于等于5”的要求，位置 `0` 已经符合。失败发生在有序前提被取消之后。这不说明原来的算法在约定输入下出错，却说明你的解释必须带上适用条件。

还有一种解释看似谨慎：“只要用几个例子算对了，就说明我的理由正确。”也要收紧。例子能揭露错误，有限的成功样例却不能自动覆盖所有输入。我们既要用具体输入找漏洞，也要逐步检查理由是否足以支持排除操作。

可以给自己的笔记留三小栏：原来的理由、哪个检查让它站不住、修订后增加了什么条件。不要用漂亮的新解释覆盖旧版本，否则第二天很难知道自己真正修补了哪里。若发现问题只是忘记下标从零开始，就补约定；若无法说明为什么能排除一整段，就回到有序性与目标条件。两种缺口不需要同一种练习。

还可以给每条理由标一个很朴素的状态：“我能从条件推出”“我只在例子里观察到”“我还不确定”。例如，第一次运行得到位置 `1`，属于观察；能说明为何不能漏掉更早的合格元素，才补上了这一选择的依据。暂时写“不确定”并不浪费，这会把下一次查资料或请教的问题收窄。不要为了让笔记显得完整，把猜测写成已经确认的结论。

## 留下首次答案再看参考判断

下面两个小问题仍围绕同一个任务，不要求记住完整代码。请先写出预测和理由，再运行或展开参考判断。顺着本文完成属于有提示的练习，不是独立迁移测验。

**问题一：**有人把 `right = mid` 改成 `right = mid - 1`，理由是“这个位置已经看过了，不必再找”。你认为是否安全？给一个很短的输入，说明预期结果和程序结果。

**问题二：**保持原代码不变，分别输入空数组 `[]` 和数组 `[2, 5]`，目标都为 `8`。它们会返回什么？请用开头约定解释这些结果，而不只做逐行计算。

问题一不安全。用 `[1, 3, 5]`、目标 `3`：初始中间位置是 `1`，修改后的代码把右边界设成 `0`，循环立即结束，返回 `0`；正确答案应为 `1`。当前位置虽然检查过，仍可能就是最早满足要求的位置。是否需要再检查它，与能否排除它成为答案，是两件事。

问题二分别返回 `0` 和 `2`，都等于相应数组的长度。空数组没有可选元素；第二个数组的元素都小于 `8`，同样没有符合要求的元素。这个返回值是预先约定的“未找到”位置，不能接着不加检查地用它读取数组元素。

对照时，别只记“答对两题”。看看自己能否说明保留候选的理由，是否使用了排序前提，以及是否记得未找到时的约定。答案错了，也尽量标出第一处无法自圆其说的地方，比事后写一句“边界没处理好”更具体。

如果想过一天再检查，请另换没有见过的输入或一小段新代码，先保存首次作答，再看提示。今天已经展开过的答案，明天重做只能算复习；不能因隔了一夜，就称为盲测。一次个人练习也不能证明某种教学方法造成了能力提升，更不能用来诊断智力。

## 给解释找一个核对对象

自己暂时补不出理由时，可以查教材、请同伴追问，也可以让 AI 找反例。但最好先留下自己的解释，再提出具体请求，例如：“我认为可以删掉左半边，因为中间值太小。请检查我有没有漏掉前提，并给出能推翻它的输入。”

若直接让 AI 讲解整段代码，再把它的回答读顺一遍，留下的仍可能只是另一段熟悉的讲解。把回答当作待核对的建议：能运行的例子亲自运行，声称适用于所有输入的理由继续查条件。AI 提出的反例也可能不满足题目约定，需要同样检查。

你也可以把讲解分成两轮：第一轮只请对方指出最需要补理由的一步，不直接给答案；自己补完后，第二轮再核对。这样能留下你的首次推理，也更容易看清帮助究竟发生在哪里。若最后依然需要看完整讲解才能继续，就把这次记为带帮助完成，而不急着给自己贴上“已经掌握”的标签。

这次可以带走四点：

- 复述帮助确认读到了什么，进一步解释要交代条件如何支持这一步。
- 优先解释会影响正确性的选择，不必机械地给每行代码配长篇说明。
- 把解释写成可以被反例挑战的判断，再用运行结果与逐步推理修订它。
- 保留首次答案和修改痕迹，把复习、有提示练习与独立完成分开记录。

下次看懂一个答案，不妨挑其中最关键的一步，先把“它做了什么”放在一边，试着回答：如果我改动这一步，最小的失败例子会是什么？若暂时找不到，也把还缺哪条理由记下来。理解的检查可以从这样一个具体问题开始。
