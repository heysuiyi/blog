资料于北京时间2026年10月30日晨间核验；新闻优先采用UTC10月29日官方发布内容，近期补充另标原始日期。教学例子使用虚构、已脱敏的客服工单。价格与接口限制引用核验时的官方文档，示例数量与架构参数是教学假设，不是实测吞吐、账单或服务保证。本期没有调用付费模型API，也未运行真实队列或UI无障碍测试。

## 1 AI与软件工程新闻

 **10 月 29 日的两组更新，把焦点从“模型能做多少”移到了“动作怎样受约束”。**  OpenAI 更新 Model Spec，并公开前沿模型失配行为的监控架构；Vercel 则调整智能体运行时与沙箱的分工。前者是行为规范与安全工程披露，后者是开发框架更新，都不应被包装成新基础模型发布。以下按官方原文日期，核验于北京时间 10 月 30 日 06 时许。

OpenAI 新版 Model Spec 增加对上下文、人类自主性和行动副作用的指导，同时删减大量细碎风格规则。重要的限制写在公告里： **规范描述的是努力实现的行为，现有模型还没有完全符合它。**  对工程团队而言，提示词里的行为要求不能替代权限控制。[Model Spec 更新，10 月 29 日](https://openai.com/index/updated-model-spec/)

同日的监控报告更接近真实系统：先用轻量探针筛查，再由模型审阅对话与工具使用，调查智能体重建过程，必要时结合网络日志等外部证据升级处理。它不是“让模型自己说有没有违规”；也不是监控覆盖了就必然能阻止行动。官方特别说明，对纳入该监控的外部部署，Responses API 的自动暂停依赖受支持的会话追踪方式；没有这些机制，告警发出后对话仍可能继续；该系统不覆盖 Chat Completions API。 **本期判断：接入智能体时，应把发现异常、停止执行、人工复核分别设计和验收，而不是把“有安全监控”当成一个总开关。**  这是一项依据架构作出的工程判断，并非本期实测。[监控架构报告，10 月 29 日](https://openai.com/index/how-we-detect-frontier-model-misalignment/)

Vercel 的变化则更具体：AI SDK 的 fx 适配器改用 libfx。这里的智能体运行框架（harness）负责把模型与工具执行连起来；宿主进程是运行这个框架的主程序，沙箱则是隔离执行命令的环境。更新让运行时和模型请求留在宿主进程，内置文件与 shell 操作仍在沙箱内执行；模型凭据留在命令执行环境之外，也不再需要沙箱内的桥接进程或暴露端口。更新同时提供工具过滤、执行中追加指令及会话恢复等能力。但文档仍把 harness 包标为 **实验性** ，提醒可能发生破坏性变更；宿主还需要访问模型网关及所配置的 MCP 服务；后者通过约定的连接协议提供外部工具或数据。因而，这改善的是执行边界，不是证明系统已经离线或绝对安全。试用时值得先核对“凭据在哪里、哪些工具可写、哪里能联网”，再测完整任务是否可靠恢复。[Vercel 更新，10 月 29 日](https://vercel.com/changelog/fx-harness-adapter-now-separates-host-and-sandbox)、[fx 官方文档，10 月 29 日核验](https://ai-sdk.dev/providers/ai-sdk-harnesses/fx)

## 2 模型特性与开放权重

本期聚焦  **Mistral Large 4（Le Chonk）** 。三个时间点必须拆开：模型在  **10 月 6 日** 进入公开预览；Mistral 官方权重仓库的  **10 月 29 日** 提交记录出现初始发布，现有文件树也已列出实际权重分片；Vercel 同日确认 AI Gateway 的既有模型 ID 接入更新权重。因此，今天不只是又一家平台添加同名模型，但也不能称所有服务都已正式可用——核验时，Mistral API 模型页仍标注 Public Preview。[最初预览公告](https://mistral.ai/news/mistral-large-4/)、[权重发布记录](https://huggingface.co/mistralai/Mistral-Large-4-1T-A52B/commits/main)、[当前 API 模型页](https://docs.mistral.ai/models/mistral-large-4-0)

权重是模型学习后保存的参数文件，下载它们才有自行运行模型的基础。Mistral Large 4 的实用特性，是把图文理解、推理和工具调用放在同一组权重中：接受文本和图像，输出文本；支持函数调用、严格 JSON schema（约束返回数据的字段、类型和结构），以及 low、medium、high 三档推理投入，默认 high。对设计工程协作，这意味着可以把界面截图或技术图与修改要求一起交给模型，并约定结构化返回格式； **不意味着模型原生生成了图片，也不意味着返回的 JSON 已经通过业务校验。**  原厂强调新版强化了智能体编码、防御性安全任务和 token 效率，但这些仍应在自己的仓库、测试集与运行配置下验证。[官方模型卡，10 月 29 日核验](https://huggingface.co/mistralai/Mistral-Large-4-1T-A52B)、[新权重发布说明](https://mistral.ai/news/mistral-large-4-oss/)

开放权重提供的是自行部署和定制的选择，不是零成本，也不是没有条件的 MIT 开源。实际许可证是  **Mistral Ecosystem Open-Weight License** ：若使用方或其关联公司经营 Model-as-a-Service（对外提供托管模型服务），商业用途须按条款另获许可；条款另列内部使用、经官方产品访问等例外。准备做托管模型服务时应核对完整条款，不能把“能下载”当成“能任意转售”。[官方许可证，10 月 29 日核验](https://huggingface.co/mistralai/Mistral-Large-4-1T-A52B/blob/main/LICENSE)

另一条路是继续使用托管网关。Vercel 表示，已有 `mistral/mistral-large-4` 无需改名就会使用新权重与新价格。便利也带来版本识别问题： **模型 ID 没变，不代表行为没变。**  本期建议保存更新前后的代表性任务、输出与测试结果，分别比较补丁正确性、工具调用稳定性和总 token 消耗；有条件再评估自托管，而不是仅因“开放”就迁移。网关负责接入与运维，模型负责推理，两者都不能替团队完成最后的验收。[AI Gateway 更新，10 月 29 日](https://vercel.com/changelog/mistral-large-4-updated-weights-and-lower-pricing-on-ai-gateway)


## 3 模型配置与批任务预算

今天先回答一个实际问题： **100 条虚构客服工单已经通过脱敏与资格检查，怎样知道这批任务交得起、交得进去？**  输入是这 100 条批准提交的工单、完整摘要规则和价格；输出不是摘要本身，而是一张“预计花费、预留额度、是否允许提交”的预算记录。本节的 100 条全部合格；UI 章节会另举“100 条候选中有不合格项”的入口例，不是这里漏减了数量。

沿用上期 Claude API 的 `claude-sonnet-5-5` 与版本头 `2026-10-21`，不再重讲创建和领取接口。以下资料核验于  **2026 年 10 月 29 日 UTC** ；数量、用量与应用限额都是教学假设， **没有调用模型 API 或进行性能实测** 。[模型说明](https://platform.claude.com/docs/en/models/sonnet-5-5/overview)、[API 版本](https://platform.claude.com/docs/en/api/versioning)

### 先算预计花费 再做提交预留

 **Token 是模型处理文本的计量单位，不等于汉字数。**  输入要算工单和每条重复携带的规则，不能只算正文。实际接入可用官方计数能力估计完整输入，但计数不是未来账单的保证。本例假设每条输入为 1,200 token，平均输出为 800 token，且没有缓存、工具调用及其他收费项。[Token 计数说明](https://platform.claude.com/docs/en/build-with-claude/token-counting)

为什么三句摘要会预算 800 个输出 token？因为 Sonnet 5.5 默认开启自适应思考，输出预算必须把内部思考和最终文字一起算进去。800 是本例对 **总输出** 的假设，不是“800 正文再加免费思考”。当前官方 Batch 价格为每百万输入 token  **1 美元** 、每百万输出 token  **5 美元** ；对应标准价为 2 美元和 10 美元。[官方价格](https://platform.claude.com/docs/en/about-claude/pricing)、[思考与计费](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost)

分三步算：

1. 输入共 `100 × 1,200 = 120,000` token，费用为 `120,000 ÷ 1,000,000 × $1 = $0.12`。
2. 预计输出共 `100 × 800 = 80,000` token，费用为 `80,000 ÷ 1,000,000 × $5 = $0.40`。
3. 合计预计  **$0.52** 。这是规划数字，不是已扣款。

 **预留** 则是先占住可能需要的钱，防止多个任务同时花同一笔余额。若每条仍用上期示意的 `max_tokens: 4096`，按总输出上限计算，一次尝试的预留为 `$0.12 + 100 × 4096 ÷ 1,000,000 × $5 = $2.168`。这个值只在上述输入假设成立、无额外收费时适用，不是整项业务的绝对封顶；重试、输入计数差异都要另留空间。`max_tokens` 同时约束思考和正文，不代表每条必定花满，也不保证摘要不被截断。[输出预算边界](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost)

假设应用今天只批准花 $3，准备首次 100 项及最多 10 次单项补做尝试，可先预留 `110 × $0.02168 = $2.3848`，另留输入误差余量。真正收到结果后，用各次尝试的 `usage` 对账，再释放未用预留；别按摘要可见字数结算，也别把 `usage.output_tokens_details.thinking_tokens` 又加到已包含它的 `usage.output_tokens` 上。若假设首轮最终输入为 120,000、总输出为 70,000 token，则首轮模型费为  **$0.47** ，不是 $0.52 或 $2.168；这仍是假设账例。[usage 计费口径](https://platform.claude.com/docs/en/build-with-claude/thinking-steering-and-cost)

提交前应检查“已结算花费＋其他任务预留＋新任务预留＋误差余量”是否仍在批准预算内。已有预留不能因为另一个工作器看不见它就重复花掉。官方也提醒，批处理并发可能略微超过控制台的 Workspace 花费限制；因此平台限额不是应用级绝对保险，严格预算要留安全边际并控制新准入。[批处理花费边界](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

### 有钱不等于有吞吐额度

把几种限制分别记账：美元预算管花费； **RPM**  管每分钟请求次数；普通 Messages 的  **ITPM、OTPM**  分别管每分钟输入和输出 token。Batch 另有跨模型共享的 HTTP 请求速率与排队单项容量，不套用普通 Messages 的 token 速率表。当前官方 Start 档列出批接口  **1,000 RPM、20 万个排队单项、每批最多 10 万项** ；这是公开档位，不是已查到你的账户额度，接入前还须核对组织与 Workspace 的实际限制。[限额文档](https://platform.claude.com/docs/en/api/rate-limits)、[批处理额度独立性](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

所以，“一个批次装 100 条”不是只占一个排队名额；反过来，100 条也不是 100 次创建 HTTP 请求。查询仍消耗接口请求额度。预算预留适合重复任务、多人共用额度的生产系统；一次性人工试验可以简化记录，但不能把廉价、剩余配额或预留金额当成交付时限。

另一个常见混淆是：本地按 `max_tokens` 预留美元，不等于供应商按它预扣输出速率。普通 Messages 的 OTPM 根据实际生成输出计算。一个管“还敢承担多少钱”，另一个管“当前生成得有多快”，不要共用一个余额字段。[OTPM 计算口径](https://platform.claude.com/docs/en/api/rate-limits)

## 4 架构设计与排队背压

现在把问题扩大：客服持续送来已合格工单，而模型、验收与数据库不一定同速。输入是不断到来的任务；输出应是可追踪的已交付摘要，或明确的等待、拒收原因，不能只是不断增长的任务列表。以下容量与策略是 **应用设计示例，不是供应商保证** 。

### 三个词分别管什么

 **队列** 存放等候处理的工作； **并发** 是同一时刻正在处理多少项； **速率限制** 是在一段时间内允许启动多少项。四个工作槽不等于每秒四项：每项耗时不同，速度就不同。BullMQ 的本地并发只限制单个 Worker；多进程共用时，还要考虑全局并发。它的队列限流也不是给每个 Worker 额外复制一份额度。[本地并发](https://docs.bullmq.io/guide/workers/concurrency)、[全局并发](https://docs.bullmq.io/guide/queues/global-concurrency)、[队列限流](https://docs.bullmq.io/guide/rate-limiting)

可把应用分成“入队检查 → 提交批次 → 等待远端 → 领取验收 → 写库”。建议分别管理 **短暂的提交工作槽** 与 **远端未对账单项名额** 。例如，最多两个工作器同时发送创建请求，另限制本应用最多有 200 个已提交但尚未对账的单项。创建成功、保存批次凭证后，可以释放工作槽；但那 100 个单项的名额和费用预留仍然占着，不能因为 HTTP 返回就释放。提交结果未知时也先保留占用，按上期的方法查明。

这尤其容易误读：两个提交工作器可以迅速送出多个批次， **不表示 Anthropic 会同时运行两条或两百条模型任务** 。远端怎样调度，不由本地 Worker 数量决定。200 是我们主动选择的保守在途上限，既不是官方配额，也不是并发承诺。

同样，两个批次各有 100 项，输入长度却可能相差十倍。按项数限队列便于管理业务进度，但不能替代 token 和费用预留。长工单要重新估算，不能因为“还有一格”就认定资源足够。

### 队列只能吸收波峰 不能修复长期超载

做一个只看瓶颈的理想化算例，暂不考虑前章的 $3 预算闸门。假设本地预处理有四个槽，每项两秒，能力为 `4 × 60 ÷ 2 = 120 项/分钟`；验收写库只能完成 80 项/分钟。即使远端一直及时提供结果，整条链路也至多交付  **80 项/分钟** ，不是 120。这是算例假设，不是 Batch 的服务承诺。

如果每分钟仍批准进入 100 项，未交付工作就至少增加 `100 − 80 = 20 项`。我们给“待提交、远端在途、待验收”的总和设 300 项上限；当前已有 100 项，剩余 200，至多十分钟就会用完。真实系统有波动，不能把十分钟写成精确预报。把上限改为 3,000 只会推迟满载，还可能让工单等到失去业务价值。

 **背压** 就是让下游的拥堵反过来约束上游，而不是继续收单后悄悄拖延。本例在总量达 240 时暂停自动导入，降至 160 才恢复；不同阈值避免刚停就开、反复震荡。它们是应用阈值，不是 API 参数。入口需要原子地检查并占用容量与预算，防止两个进程都看见“还剩一格”而同时放行。手动提交若超限，应保留用户选择并说明等待原因，而非丢弃任务或假装已提交。

容量暂满可以等待；日预算耗尽则需要等下个预算周期或重新授权，盲目重试不会解决。对可重试的限流响应，遵守实际返回的等待提示，重试也走同一限流器；不要复制一批新任务绕过拥堵。已有任务继续领取和对账，不能把“暂停新提交”实现成“所有工作都停下”。[限流响应说明](https://platform.claude.com/docs/en/api/rate-limits)

这种设计适合持续导入、突发流量或共享下游资源；仅偶尔人工处理一小批时，可以先用持久任务表和单工作器，不必立刻搭复杂队列。 **自检：** 如果等待队列变短，但远端在途和待验收不断增加，系统变健康了吗？没有，只是工作换了位置。应一起观察未交付总量、最老任务等待时间、实际交付速率与已占用预算，再决定减速还是扩容。


## 5 大厂UI设计

用户在第一页勾了几条工单，翻到第二页后按“批量生成”，到底会处理谁？长列表的风险不在复选框难懂，而在 **看见的行、选中的对象与实际执行的对象不一定相同** 。本期仍用100条虚构、已脱敏工单练习，学习在提交前把这三者对齐；下文每页20条、94条可生成的数量均为本节自拟，不是上一期执行结果。

### 先说清全选的范围

多选适合把同一动作施加给若干独立对象，例如按相同规则生成摘要；若每条都要作不同判断，逐条处理更合适。复选框只标记待操作对象，勾选不应立即发起模型任务。Ant Design将Checkbox用于多值选择，其Table默认通过点击复选框选择行，而不是点击整行。查看工单详情与选择工单因此可以保留不同入口。[Checkbox说明](https://ant.design/components/checkbox/)、[Table选择示例](https://ant.design/components/table/#components-table-demo-row-selection)

假设筛选结果共100条，4条正文缺失、2条已有生成任务，暂不可再次生成；第一页20条中有2条不可选。本例将表头命名为“选择本页可生成工单”，按下后显示“已选本页18条；本页另有2条不可生成”。旁边再提供独立入口“选择全部筛选结果中的94条可生成工单”。第二次操作才扩大范围，不能让一个没有限定词的“全选”悄悄跨过五页。

表头复选框的半选态表示 **本页可选项只有一部分被选中** ，不表示加载中，也不代表某条工单只处理了一半。全部18条可选项已选时，本页表头可显示全选，即便还有2条禁用项；可选范围必须在标签与数量中说清楚。Ant的`indeterminate`提供半选状态；WAI APG说明群组复选框可用未选、部分选中、全选表达组内状态，并要求相应名称与状态可被辅助技术识别。这里的“组”限定为本页可选项，是本文设计，不是它们替产品决定的分页规则。[Checkbox API](https://ant.design/components/checkbox/#api)、[APG Checkbox模式](https://www.w3.org/WAI/ARIA/apg/patterns/checkbox/)

### 翻页不等于忘记 但筛选改变要交代

本例允许跨页累积。选完第一页18条再到第二页，持续显示“共选18条，本页0条”，并提供“查看已选”和“清空选择”；第二页表头仍未选，不能用全局数量伪装成本页已选。选择记录跟随稳定工单ID，不跟随“当前第几行”，否则排序后可能勾到另一位客户的工单。

Ant的`selectedRowKeys`用于受控选择，也就是由应用保存并传回当前已选ID；`preserveSelectedRowKeys`可在记录离开`dataSource`（当前载入的数据列表）时保留所选key，即对象标识。 **保留标识不等于自动选择服务器全部结果，更不保证对象仍有执行资格。**  数量、跨页清单与资格检查仍须由应用管理。[Table rowSelection API](https://ant.design/components/table/#rowselection)

本例另定一条容易解释的规则：翻页和排序保留选择，应用新的筛选条件则清空。为避免白选，在应用新筛选前提示“更改筛选将清除已选18条”，让用户选择“更改并清除”或“保留原筛选”。这不是所有产品都必须遵守的规范；关键是不让筛选外的隐藏对象在用户不知情时继续参与批处理。选择全部结果时，应用还应固定当时的工单ID清单，之后新增的匹配工单不自动加入；想处理新记录，需要重新选择。

### 不能操作的条目要解释 提交要说出对象

禁用复选框旁保留“正文缺失”或“已有任务处理中”等文字，并给出相应查看入口，不只靠灰色或鼠标悬停解释。批量栏显示“已选94条；另有6条不可生成”，还能查看这6条。不要先写“已选100条”，提交后才无声跳过6条；“选中了多少”和“为什么没选”都是任务范围的一部分。这些反馈文案是本例建议。

本例生成会消耗模型配额，因此提交前提供一次范围复核：显示当前筛选条件、已选94条、未纳入的6条及原因，并能打开完整已选清单。按钮写“为94条工单生成摘要”，而不是“确定”。不是每次勾选都要弹窗；低成本、可轻易撤销的动作可用清楚的操作栏直接执行。

提交前仍要复核资格。若94条中又有1条被其他人启动任务，应说明是哪一条、为什么不可执行，更新为93条并让用户重新确认，不暗中改变这次操作的对象；最终是否可以执行仍由服务端判定。提交后的反馈也应对照这份确认清单，而不是拿此刻屏幕上20行冒充整个批次。

 **手工练习：** 先在纸面画两页，各20行，第一页标2条不可选。选本页后翻页，正确结果是总数18、本页0；返回应仍看见原18条。再模拟选择全部94条，增加一条新工单，已选数仍为94；模拟一条失去资格，复核应要求确认93条的新清单。最后应用新筛选，确认先提醒再清空。用键盘和屏幕阅读器复查时，还要检查表头读出的范围、半选状态和变化后的数量，而不是只看颜色；本练习尚未执行。

## 今日小实验

不调用模型，也能先检验一次批量操作能否说清对象和资源。画一个含100条候选工单的列表，按UI课的条件标出6条不可生成；选中剩余94条后，再模拟其中1条已有别人的任务。此时先说明对象变化，请用户确认93条的新清单，而不是偷偷少做一条。

这一次才把第三节的单项预算假设套到确认后的93条上：每项预计成本为0.0052美元，预计合计0.4836美元；每项首轮预留为0.02168美元，首轮共预留2.01624美元。这里仍假定每项输入1200 token、无缓存与额外收费，重试和误差余量另计。数量变化以后，预算也要随之变化，不能仍沿用候选100条的金额。

然后假设系统的在途容量已经占满，但预算仍足够。正确处理是保留这93条选择和预算估算，告知暂时不能提交；不要显示“已开始生成”，也不要重试创建一个新批次来绕过容量。等有容量时，实际提交前再次检查权限、内容版本和资格；若清单再次改变，返回范围复核，不沿用过时确认。

这份练习的参考判断不是只有乘法算对。界面的确认清单、预算使用的项数、后台接收的稳定工单ID应一致；资源占用也应能解释是谁占了多少。可在纸面上列出这些记录，检查任何一步是否悄悄换了对象。上述金额已作算术核对，但完整交互与系统流程尚未实现或实测。

## 今天记住这四点

- 行为规范、安全监控与执行权限各有作用；规范更新不代表当前模型已完全做到。
- 模型开放权重、API预览与网关更新是不同发布事件，接入名称没变也要留意行为变化。
- 预计费用、应用预留、供应商速率与队列容量分别计量；暂停准入以后，已有任务仍要继续领取和对账。
- 批量操作先说清选了哪些对象，再计算预算与创建任务；本页全选不能悄悄变成服务器全选。
