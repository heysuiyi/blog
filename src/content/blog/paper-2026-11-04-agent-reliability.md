一个鲜花订单助手收到请求：“把配送改到11月12日上午，卡片内容保留。”它查了订单，调用修改工具，最后回复“已经改好”。演示顺利结束。

但再运行几次，情况可能变了：有时它只说改好了，订单没有变化；有时日期改对了，却顺手改了卡片；还有一次，结果完全正确，但它跳过了流程要求的确认。我们该把这些表现算成同一种“成功”吗？

本篇读 τ-bench，一项把用户对话、工具调用和业务规则放进同一测试环境的研究。它适合帮助我们追问两个问题：**成功究竟由什么证据判定，同一个任务重复执行时能否持续成功？** 鲜花案例是本文独立设计的教学场景，不是论文里的任务，也不涉及真实订单。

## 先确定我们正在测什么

这里的 Agent，指能够根据对话选择下一步、调用工具并处理返回结果的系统。模型是其中一部分，提示词、工具接口、业务规则和执行程序也会影响表现。说“这个 Agent 得了多少分”，应当连同这些配置一起说明，不能只报一个模型名。

工具可以只读，也可以写入。查订单是只读；改配送时间是写入，会改变系统状态。一次任务中，用户说过的话、工具调用及其返回、Agent 的回复，合起来称为**执行轨迹**。轨迹告诉我们事情怎样发生，最终状态告诉我们结束时系统变成了什么样。

还要区分“重跑”和“重试”。本篇的重跑，是把数据库和对话恢复到同一个起点，再独立完成一次任务。它不是在刚才失败的真实订单上继续尝试，也不是让模型看着上次答案修正。这个区别直接决定后面的可靠性指标有没有意义。

## 论文怎样把一次服务变成一道可检查的题

Shunyu Yao、Noah Shinn、Pedram Razavi 和 Karthik Narasimhan 提出的 τ-bench，于2024年先行公开预印本，后发表于 ICLR 2025。本文依据会议正式版本解读，不把它当成2026年的最新模型排行榜。

研究包含零售和航空两个合成领域，分别有115项和50项任务。研究者设计数据库、可执行的工具和政策，再编写用户目标与正确结果。Agent 能读政策、调用工具，却看不到测试用的目标答案；另一个语言模型扮演用户，随对话逐步提供信息、表达偏好或作出确认。[环境与任务构造，正式版第3—6页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=3)

这比“给定一句完整指令，输出一个函数”多了一层难度。Agent 可能要先问清需求，再查业务限制，再取得确认，最后才能写入。有些限制由工具拦截，有些只写在政策里，需要 Agent 自己遵守。**工具调用成功，并不自动表示这次调用在业务上应该发生。**

原研究默认用 gpt-4-0613 模拟用户。主要实验中，每项任务至少运行3次，每次最多30个 Agent 动作，动作包括工具调用或对用户的回复；Agent 的采样温度为0，用户模拟器为1。即使 Agent 设置得较确定，对话仍可能变化，因为它面对的用户回复会变化。这里测到的是整套交互系统在这类变化下的表现。[实验配置，第3、7页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=7)

任务结束后的自动评分主要检查两件事：最终数据库是否与标注的目标状态一致，以及回答是否包含任务要求告知用户的信息。原文示例的信息检查采用字符串包含判断。它让测试不必强制所有 Agent 说同一句话、走同一条路径，但也不会因为回复听起来流畅，就直接判为完成。[评分定义，第4—5页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=4)

这里有一个不能略过的限制。作者明确指出：**自动得分为1，仍可能没有满足全部政策。** 例如，Agent 未经用户明确确认就执行退货，最终数据库却可能恰好正确。因此，这个得分是研究中定义的成功，不是完整的合规证明。检查答案以前，先检查评分规则漏掉了什么，是本文最值得保留的阅读习惯。

## 平均成功与重复成功回答不同问题

正式版表2中，gpt-4o 函数调用 Agent 的零售成功率是61.2%，航空是35.2%，两领域等权平均为48.2%。这里的平均不是把165项任务直接混在一起计算。论文摘要里“低于50%”也不能改写成“零售任务低于50%”。[主要结果，表2，第7页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=7)

这些是历史实验在特定环境和评分口径下的结果。它们不能直接预测一个今天部署的助手，更不能单凭模型名称比较新旧系统。真正值得学习的是作者怎样进一步检查“有时会做”和“反复都能做”的差距。

常见的 **pass@k** 问的是：同一任务独立尝试 k 次，至少有一次成功的概率是多少？τ-bench 提出的 **pass^k** 问的是：这 k 次全部成功的概率是多少？两者都先针对同一任务，再在任务之间取平均。k 是完整任务的次数，不是一次对话里的工具调用数，也不是连续 k 个步骤。

一个适合反复生成候选、由可靠检验器挑选结果的系统，可能关心“至少找出一个正确答案”。直接服务多次请求的助手，还需要知道“每次能否都办好”。后者通常不能把失败记录丢掉，只展示最好的一次。

用一组完全虚构的记录算一下。假设同一个任务恢复初始状态后运行4次，结果依次是成功、成功、失败、成功。单次成功比例是3/4，即75%。从4次记录中任取两次，共有6种组合：

| 取出的两次 | 是否全部成功 | 是否至少一次成功 |
| --- | --- | --- |
| 第1、2次 | 是 | 是 |
| 第1、3次 | 否 | 是 |
| 第1、4次 | 是 | 是 |
| 第2、3次 | 否 | 是 |
| 第2、4次 | 是 | 是 |
| 第3、4次 | 否 | 是 |

于是，按论文的组合估计方法，这个任务的 pass^2 估计为3/6，即50%；pass@2 估计为6/6，即100%。同一组记录，没有互相矛盾，只是“全部成功”和“至少一次成功”要求不同。这里按有限记录中不同两次的组合来估计，并不是把75%直接平方。[指标定义与估计式，第5页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=5)

这里的100%不是下一次必然成功的保证，50%也不是已精确测定的真实概率；4次数据非常有限。正式的概率解释还依赖独立同分布等条件，也就是每次来自同样的测试安排，不把上次运行的状态或答案带进去。恢复起点也不自动保证独立，不能重复播放同一份随机对话，充当多次独立样本。若几次之间改了提示词、换了模型，或者故意加大难度，就不能直接按同一口径合并。

原论文的零售结果显示，gpt-4o 函数调用 Agent 的平均单次成功率超过60%，但 pass^8 低于25%。这来自图4的重复实验：估计 pass^8 至少需要每任务8次记录，不能拿表2所述的最低3次直接算出。原文没有统一列明图4各模型的确切重复次数，本文不补猜。

这反映了重复成功的要求更难满足。它不是“连续调用8个工具只剩25%成功”，也不是“允许重试8次的成功率低于25%”。更不能把总平均成功率直接连乘8次来复现图中结果，因为不同任务的难度并不相同。[图4及正文，第7—8页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=7)

## 把鲜花助手的验收条件写清楚

现在把这个思路用于开头的教学案例。所有数据都在纸面或本地沙盒里，不连接真实商家。假设身份验证已经完成，对话只涉及本人一笔虚构订单“花单27”；当前配送是2026年11月10日下午，状态为“待制作”，卡片原文为“生日快乐”。用户希望改为11月12日上午，卡片不变。新旧时段价格相同，不涉及收费或退款。

为了让任何人都能检查，本例规定四条业务政策：只有“待制作”的订单允许修改；目标时段必须有余量；执行前必须列出具体改动并得到用户明确确认；没有获准修改的字段必须保持原值。这里的确认要求是本例明确规定的规则，不是对所有行业流程的概括。

助手有三种工具：查询订单、查询可配送时段、更新订单。更新工具技术上可以修改日期、时段和卡片，并检查订单状态与时段余量，但不会检查聊天里有没有用户确认。本例另约定：更新失败时不改任何字段，工具明确返回成功或失败；查询工具只读。这样设计，是为了保留一个真实的测试难点：**接口允许做的事，可能比这次任务授权做的事更多。**

先别急着写提示词。把预期结果写成一句可核对的话：“得到用户确认后，将花单27的日期和时段改为11月12日上午，卡片及其他字段不变，并如实告知结果。”再把它拆成三个检查面：

- **最终状态：** 日期、时段正确，卡片仍是“生日快乐”，其他字段没有额外变化。
- **执行过程：** 确认发生在写入之前，且确认对象就是这笔订单和这组改动；没有发生未经允许的写入。
- **对外说明：** 完成声明有工具执行结果支持；若没有修改成功，就不能说“已经改好”。

这三个面应分别记录，最后再决定整体是否通过。只看“11月12日上午”这个字段，会漏掉卡片被改；只看最终数据库，会漏掉先写入、后补问确认；只看回答，会把根本没有落库的承诺算成成功。即使后来把错误字段改回去了，最终状态也不能抹掉先前发生过的越权动作。

这是对原论文评分盲点的教学扩展，不是声称 τ-bench 已经完整实施了这三类检查。实际系统还可能有邮件、配送通知、收费等数据库之外的副作用，需要另设可观察的证据；本例刻意不包含这些外部动作。

## 做一次小而能定位问题的实验

可以先请同伴扮演用户和工具，也可以在本地用固定数据模拟。若只是人工演练，就把结果记为“流程演练”，不要称为模型测评。若确实接入 Agent，应记录模型版本、提示词、工具定义、采样设置和运行日期，并在整轮检查中保持不变。

先准备四种情况，每种都有自己的初始数据和用户回应。它们是覆盖不同条件的测试题，不是同一任务的四次重复。除表中差异外，都沿用上一节的订单、请求和政策。

| 情况 | 改动的条件 | 预期处理 |
| --- | --- | --- |
| 甲 | 待制作，目标时段有余量，用户在方案明确后确认 | 改日期与时段，保留卡片和其他字段 |
| 乙 | 待制作，目标时段已满，用户不接受其他时段 | 不写入，说明该时段不可用 |
| 丙 | 已开始制作，目标时段有余量 | 不写入，说明当前状态不允许修改 |
| 丁 | 待制作，目标时段有余量，用户看完方案说“先别改” | 不写入，说明尚未修改 |

测试前，由出题者保存每种情况的初始状态、预期结束状态和用户回应规则，避免临场为了“帮 Agent 成功”改答案。扮演用户时，可以自然表达，但不能把“不接受其他时段”悄悄改成“下午也行”。若要测试新的偏好，就把它记成新任务。

每种情况分别恢复起点、重跑3次，得到12条记录。这只是方便开始的小规模安排，不是论文建议的充分样本量。每次都保存三个检查面的结果和失败证据，不要失败后一直重跑，直到攒够3条成功记录。中途修了提示词，就结束这一轮，另记新版本。

先看一遍全部轨迹，再汇总。一次失败可能来自目标时段查错、未等确认、额外字段修改，也可能是扮演用户的人没有遵守脚本，或工具模拟器返回了错误数据。应保留原始失败，并标明原因。发现测试数据有错时修正它，重新运行受影响的比较，不要把测试缺陷全算在 Agent 头上，也不要为了提高分数随意删除困难题。

这轮可以设一个明确但有限的继续标准：12次都满足各自预期；所有应保持不变的字段都未变化；没有未经确认的写入；回复与实际执行一致。满足后，只说明“这一版本通过了这组小型检查”，可以继续增加新情况，不能据此宣布生产可用。即使12次全对，样本覆盖不足仍然存在。

为了检查自己是否理解，可以再问：乙、丙、丁都没有修改订单，是否都算失败？答案是否定的。它们的正确行为本来就是不修改，并清楚说明原因。反过来，甲若把日期改对，却跳过确认，依然没有通过本例的完整验收。**成功应服从任务目标与约束，不能简单等同于“做了一个写入动作”。**

## 从失败记录走到下一步改进

当失败类型清楚了，改进才有落点。若经常漏确认，可以考虑让执行程序检查确认是否对应当前方案；若经常误改卡片，可以缩小本任务工具允许写入的字段；若总是把不可用时段当可用，就检查工具返回与选择逻辑。这些是由案例得到的工程思路，不是论文已经验证有效的改进方法。

若要比较修改前后，至少固定测试任务、用户回应规则和通过标准，把两个版本的全部记录留下。还应安排未用于调试的新情况，例如用户确认前改变目标日期、请求中途撤回，或工具明确返回失败。新情况也需要先写清规则与预期，不能只说“多测几个边界”。

看到某个版本分数上升，还要问：改变的是模型、提示词、工具约束，还是评分标准？如果把“先确认”从验收里删掉，分数会变好，却没有证据说明助手更可靠。更复杂的 Agent 架构也不自动更好；这篇论文揭示了困难，并没有替所有业务选出一套最佳架构。

论文自身的范围同样需要保留。两个领域的政策和数据经过简化；用户由模型模拟，不是现实用户样本；任务设计追求唯一目标状态，但现实中可能存在多种合理处理；自动评分没有覆盖所有合规要求。任务构造还使用了特定 Agent 帮助修订用户指令，作者承认这可能带来偏向。它是一种有用的压力测试，不能代替真实场景中的全面验证。[讨论，第9—10页](https://proceedings.iclr.cc/paper_files/paper/2025/file/1b126cc38b8638e07bef37e7b2bb72bf-Paper-Conference.pdf#page=9)

## 本期可以带走的四点

- **先写成功条件，再看表现。** 状态、过程和对外说明各自需要证据，工具返回成功或回复流畅都不够。
- **“至少做对一次”和“每次都做对”是不同目标。** pass@k 与 pass^k 不能混用，重复任务也不能误写成连续步骤。
- **重复运行必须恢复起点。** 保留全部结果和配置，不把失败后的修补、换版本或改任务混成同一轮。
- **得分的边界就是结论的边界。** 小测试通过不代表生产可靠，旧论文分数不代表当前模型水平，评分漏掉的要求也不会被高分自动补上。

下一次演示成功后，可以先不问“要不要再加一个 Agent”，而是保存这一条完整轨迹，写清楚哪些字段必须改变、哪些必须保持不变、哪些条件必须先成立，再从同一起点重跑。这样才能看见：系统已经稳定完成了什么，还有哪一处只是碰巧顺利。
