## 1 科研技术与科技新闻

本期新闻检索以北京时间 2026 年 10 月 25 日 06:00 为截止点，优先检查近 24 小时的 AI 与软件工程更新。在本轮查看的官方公告中，没有核实到足够可靠、且能确认严格落在这一时间窗内的新模型首发；以下两条采用 **10 月 23 日的近期补充**。原文仅标日期，无法由此确定精确发布时间，不把它们包装成“刚刚发布”。

### 1. Copilot 开始补齐第三方客户端的模型流量账

GitHub 在 10 月 23 日宣布，Copilot usage metrics API 新增 `totals_by_client`，能够覆盖包括 OpenCode 在内的更多客户端。报告可按客户端查看成功模型请求、会话、输入输出 token，并继续按模型拆分；这是一项已公布的产品/API 改进，不是基础模型能力升级。[官方更新，2026-10-23](https://github.blog/changelog/2026-10-23-usage-metrics-api-adds-usage-from-tools-like-opencode/)

最有价值的不是多了一张表，而是修补了一种统计盲区：开发者通过不同工具使用同一个模型供应入口时，只依赖编辑器遥测，会漏掉 IDE 外的流量。服务端统计能够帮助团队分辨钱花在什么客户端、什么模型上。但 GitHub 特别指出，`request_count` 是模型调用数，不是用户发出的提示词数；客户端标识也是尽力归类，不能当作经过验证的身份。访问这些报告还要求相应角色权限及启用 usage metrics policy。

**工程解读：** 假设甲工具每次请求调用模型两次，乙工具调用六次，乙的请求量更高，并不能直接证明员工更活跃或工具效率更高。应把“完成了多少真实任务”“返工多少”“单个成功任务消耗多少”与流量账放在一起。可观测性解决的是测量问题，绩效和质量判断仍需另外建立口径。这个例子是本文的分析，不是 GitHub 对工具优劣的评测。

### 2. GitHub Public monitoring 把泄漏发现接到处理流程 但关单不等于撤销密钥

另一条 10 月 23 日更新为 Public monitoring 增加了告警关闭/重开、活动时间线、筛选、受支持凭证类型的持续有效性检查，以及 REST API 和企业 webhook。功能仍处于 **公开预览**，面向符合条件的 GitHub Enterprise Cloud 客户，不是所有个人仓库默认都获得的能力。[官方更新，2026-10-23](https://github.blog/changelog/2026-10-23-public-monitoring-adds-triage-validity-api-and-webhooks/)

这里最容易误读的细节是：把告警标成 Fixed，只会改变企业侧的告警状态，不会撤销暴露的凭证，也不会把它从公开仓库中移除。有效性状态中的 Unknown 同样不能理解为“安全”。对团队来说，这项升级的价值是更容易把发现、优先级判断和后续处置串起来，而不是把风险一键消除。

**通用流程示例：** 系统发现一把疑似泄漏的测试服务凭证，先记录来源与影响范围，再由有权限的人员到签发平台撤销或轮换，并核查使用记录，最后补充处置证据后关单。不要让“仪表盘全部变绿”替代真实世界中的状态变化。这也为后面的架构学习提出一个问题：数据库里的任务完成，是否真的代表外部操作已经完成？

## 2 新模型与产品特性

**近期补充，发布日期 2026 年 10 月 20 日；不是近 24 小时首发。** Mistral 的更新日志将 Voxtral 3 系列的四款模型均标为 **Public Preview**：离线转写的 Mini 和 Small、实时转写的 Mini Realtime，以及语音合成 TTS。同步推出的 Voice Agents 则是托管语音流水线与 SDK。不要把“新模型家族”“SDK”和“完整可执行的业务 Agent”看作同一层。[Mistral 更新日志](https://docs.mistral.ai/resources/changelogs)

### 能力变化 不只识别一句话 还要处理说话过程

官方发布材料强调转写中的说话人区分、领域词汇的上下文偏置，以及实时场景的轮次结束判断；语音合成侧强调对语境、语速和表达方式的适配。这些改进分别解决“谁说了什么”“专有名词是否听准”“用户是否说完”“输出如何被听到”等不同问题。厂商的领先性表述和基准结果应视为官方报告，不能直接推导成所有语言、噪声条件和业务音频都更好。[Voxtral 3 公告](https://mistral.ai/news/voxtral-3/)

以版本 `voxtral-mini-transcribe-realtime-3-0` 为例，模型卡列出通过 WebSocket 单次流式会话支持转写、说话人区分、上下文偏置和轮次结束检测，并提供 80–2,400 ms 的可配置延迟范围。这个范围是转写组件的配置能力，不是从用户开口到业务执行结束的整体响应承诺；模型卡仍标注公开预览。[实时转写模型卡，发布于 2026-10-20，核验于 2026-10-25](https://docs.mistral.ai/models/voxtral-mini-transcribe-realtime-3-0)

### 产品能力与模型能力 会打断对话 不等于会可靠办事

Voice Agents SDK 把采集、转写、回答模型、语音合成和播放连接起来，并支持在对话中使用工具。官方说明，各阶段串联会累积等待时间；网页、电话与自定义音频的接入方式也不同。例如电话线路上没有运行客户端工具的应用代码，因此需要的动作应使用服务端工具。语音模型本身并不会因为听清了请求，就自动拥有数据库权限或正确的业务规则。[Voice Agents 官方文档，核验于 2026-10-25](https://docs.mistral.ai/studio/audio/voice-agents/overview)

**适用与不适用的判断：** 若任务只是把已经录好的访谈变成可检索文本，应先比较离线转写的准确性与总成本，不必为了“实时”引入长连接、抢话处理和语音播放。若任务是客服实时查询订单，实时转写才有直接价值，但仍要单独设计身份核验、工具权限和关键动作确认。若每个阶段都需要自行控制，官方也提供自建流水线的路线，而不是必须采用完整 SDK。

**虚构案例：** 用户说“查询订单 4816，不对，是 4861”。一个可用的语音业务系统不能只追求尽快输出第一版文字，还应正确接收后续修正。验收至少分别查看号码最终是否正确、是否在说完前抢答、检索是否使用修正后的号码，以及失败时有没有误说“查到了”。这些是本文建议的业务测试，不是发布方已经保证的性能。真正需要采购或接入时，应拿自己的代表性样本对比，而不是只凭自然的演示音色判断整个 Agent 的可靠性。

## 3 模型配置与使用

前两期分别讨论了推理与输出预算、工具选择。本期向前一步：当任务经历多轮检索、改稿和工具调用，哪些信息应该继续进入模型？

**适用版本与边界：** 本节依据 OpenAI Responses API 在线文档，核验于 2026 年 10 月 25 日；参数示例以官方 Compaction 页面使用的 `gpt-5.3-codex` 为例，不代表所有模型、旧版 SDK 或 ChatGPT 界面都有同样选项。本文是配置说明，未实际调用 API 验证。

### 先区分 保存过 与 本次看得到

上下文窗口是单次请求可容纳的 token 空间，需要考虑输入、输出，以及适用模型的推理 token。把上一次响应 ID 传给 `previous_response_id`，可以串起对话，但不等于历史输入免费，也不等于窗口无限增长。存储负责找回历史；上下文管理负责选择这次推理使用什么，两者不是同一件事。[OpenAI：Conversation state，文档核验 2026-10-25](https://developers.openai.com/api/docs/guides/conversation-state)

可以把上下文想成工作台，而不是档案馆。做一份虚构产品的发布说明时，工作台需要当前版本的功能事实、已确认的目标读者和待解决的问题；不一定需要十轮废弃标题、完整网页导航和已经失效的草稿。这个取舍是应用设计，不是增加一个“记忆开关”就会自动完成。

### 删除 摘要和压缩 解决的不是同一个问题

直接删除旧记录最简单，但可能一并丢失早先的限制。应用自建摘要能够保留可读的“决定、证据、未决项”，也可能产生遗漏，应保留原文引用供复核。服务端 compaction 则返回用于后续推理的压缩项；该项是不透明的，并非可以逐句审计的普通摘要。

Responses API 当前文档支持在 `context_management` 中设置 `type: "compaction"` 和 `compact_threshold`，到达阈值后触发压缩。官方以 `gpt-5.3-codex`、阈值 200,000 展示用法；这只是该示例的配置，不应复制成所有模型的默认值。独立 `/responses/compact` 方式要求传入窗口仍能容纳在模型限制内，返回的整个窗口应原样用于下一次请求，不能只挑出其中一个压缩项。[OpenAI：Compaction，文档核验 2026-10-25](https://developers.openai.com/api/docs/guides/compaction)

旧代码还可能使用 `truncation`：`auto` 在超限时从对话开头丢弃条目，`disabled` 默认在输入超限时返回 400。核验时，创建请求的官方参考已将这一参数标为 Deprecated。因此，新实现不宜把它当成长任务记忆方案；维护旧实现时，也不要把“请求成功”误判为“重要上下文完整”。[OpenAI：Responses create，文档核验 2026-10-25](https://developers.openai.com/api/reference/resources/responses/methods/create)

### 一个可检查的取舍方法

以下是工程建议，不是厂商承诺：把输入分成当前指令、已确认事实、近期必要交互、按需取回材料四部分；给下一步输出和工具结果留余量，再决定何时压缩。阈值低，可能更频繁地产生压缩开销；阈值高，保留原始信息更多，但留给下一轮大工具结果的空间更少。

例如发布说明助手刚完成“功能清单确认”，便可以整理一份带版本号和来源的事实清单，让起草阶段不再依赖早期讨论中偶然出现的一句话。必须精确引用的数字仍从源材料读取，不以摘要替代原件。短小、一次性的分类任务通常不需要额外 compaction 流程；长时间编码和多轮文档任务才更值得评估。测试时应专门在压缩前放入一项关键限制，检查压缩后是否仍遵守，而不只观察费用下降。

## 4 架构设计

上一期讲失败后如何重试；这一期问更早的一件事：进程重新启动时，究竟拿什么证明工作做到哪一步？

**适用版本与边界：** 以下依据 LangGraph JavaScript 当前在线文档，核验于 2026 年 10 月 25 日。页面未提供固定 SDK 发布号，本文不虚构版本；落地时应锁定项目依赖，并按该版本核对接口。

### 三份数据 各有职责

模型上下文是本次推理的输入；图状态是工作流当前已经得到什么、接下来做什么；业务数据库则记录订单、文档版本或审批结果等业务事实。三者可以互相引用，却不宜合并成一串聊天记录。LangGraph 的 checkpointer 保存线程范围的图状态，store 则面向跨线程数据；内存版 `MemorySaver` 在进程重启后不会保留检查点。[LangGraph JS：Persistence，文档核验 2026-10-25](https://docs.langchain.com/oss/javascript/langgraph/persistence)

以虚构的产品说明生成任务为例，可把图状态设计成：资料版本、已核实事实的引用、草稿版本、审核状态、发布回执引用。不要只存一句“文章已经好了”。这份状态设计是应用自己的契约：审核的是哪一版、后续是否改过正文，都应能明确判断，而不是让模型读聊天猜测。

### 检查点保存在哪里 比 有检查点 更重要

LangGraph 在 super-step 边界形成完整检查点，恢复并非从任意一行代码继续。串行的“抽取 → 起草 → 审核”可以形成清楚的恢复位置；把整条流程塞进一个巨型节点，则难以获得同等细粒度的恢复。当前文档还提供 `sync`、`async`、`exit` 三种持久化模式：分别侧重下一步前完成写入、写入与下一步重叠、运行退出时保存。它们在写入开销与进程崩溃时可恢复的范围上有不同取舍。[LangGraph JS：Checkpointers，文档核验 2026-10-25](https://docs.langchain.com/oss/javascript/langgraph/checkpointers)

**工程推论：** 需要等待人工审核、运行较久、重算代价高的任务，适合明确检查点与持久化存储；几秒内完成、无副作用、随时可重算的小任务，未必值得先搭一整套恢复设施。节点也不是越碎越好：每一步都持久化会增加存储、序列化和维护负担，应沿着“结果值得保存、可独立验证”的业务边界拆分。

最后保留一道边界：检查点不是外部发布平台的事务凭证。若发布已成功、进程却在保存回执前崩溃，恢复后仍应查询外部状态，不能只因图中缺少回执就再次发布。这衔接了上一期的幂等原则，但本期的新增重点是：恢复方案先定义事实归谁记录，再决定在哪一步保存。可以做一次故障演练：分别在抽取后、审核等待中、发布响应后终止进程，观察系统是否恢复到正确阶段、是否误用旧审批、是否重复产生副作用。

## 5 大厂 UI 设计

前两期解决“内容放在哪里”和“何时打断用户”。这一期讨论另一个问题：页面越来越多后，用户怎样进入、切换、返回，而且不丢掉刚才的工作？导航设计的对象不仅是菜单，还包括信息层级与状态。下面将官方原则用于一个虚构的知识库产品；案例中的具体方案是设计推演，不是某家公司的现成产品规定。

### 先分清三种关系 再挑组件

全局导航回答“这个产品有哪些主要区域”，例如资料、项目、收藏。局部导航回答“当前区域里有哪些同级内容”，例如某项目的概览、文档、成员。上下文入口则由眼前对象产生，例如文章中的“查看所属项目”。这三种关系不应因为都能点击，就全部挤进同一排菜单。

组件名字也不能跨平台机械套用。Apple HIG 的 Tab bar 用于应用顶层区域切换，而 Android 官方布局指南把 Material 3 Tabs 作为同级内容分组的次级导航。Apple 还明确区分导航与动作：“新建文档”应是操作按钮，不是一个点下去就弹编辑器的顶层分区。[Apple：Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)；[Android：Layouts and navigation patterns](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns)

### 何时用标签 侧栏与面包屑

如果主要目的地不多、用户需要频繁切换，持续可见的入口有利于发现和定位。窗口变宽后，可以把紧凑的底部导航改成侧向导航，不必把手机底栏简单拉长。Android 指南强调按窗口尺寸调整导航形式；这是平台适配依据，不是所有网站都必须遵守的固定像素规则。[Android：自适应导航](https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns)

层级较多、名称较长的桌面工作台更适合侧栏。Ant Design 的 Menu 区分顶部导航与承载多级结构的侧边导航，但组件允许嵌套不意味着业务应该无限嵌套。先合并用户不关心的内部分类，比增加第四层折叠菜单更有价值。[Ant Design：Menu](https://ant.design/components/menu/)

面包屑解决的是“当前位置属于哪里、如何回上级”，不是“我刚才点击过什么”。Ant Design 建议在层级较深、需要定位或回到上级时使用。一个只有首页和详情的简洁网站，不必为了显得完整再铺一条面包屑。[Ant Design：Breadcrumb](https://ant.design/components/breadcrumb/)

### 一个完整案例 知识库里的文档详情

假设桌面左栏是“资料、项目、收藏”，进入“项目／春季活动／文档 A”后，左栏仍选中项目，标题上方用面包屑说明归属；项目页内部再用“概览、文档、成员”切换同级内容。“新建文档”放在文档列表工具区，不与三个区域混排。

用户在文档列表筛选了“待复核”，翻到第二页，再打开文档 A。我们的验收要求是：返回列表后仍能恢复筛选和页码，而不是只做到 URL 看起来回去了。切到收藏再回来，也应明确哪些状态保留。Apple HIG 强调顶层区块切换时保留各区域的导航状态，这能减少用户重复寻找位置。[Apple：Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)

还要从“别人发来的文档链接”进入一次。深链接应能直达目标，而不是必须先点击项目才能打开；登录、权限检查仍不可省略。返回历史与回到上级是不同动作：前者取决于来路，后者取决于层级。Android 文档展示了深链接及返回栈处理，但 Web 应按浏览器历史设计，不照搬 Android 的任务栈实现。[Android：Deep links](https://developer.android.com/guide/navigation/design/deep-link)

### 看得见的选中态 不等于可用的导航

真正的页内 Tabs 需要键盘与辅助技术支持：焦点进入标签组后，用方向键移动；手动激活模式用 Enter 或空格显示面板，并维护选中状态及标签与面板的关联。若每次切换都要明显等待网络请求，不宜把焦点移动直接变成自动激活。WAI-ARIA APG 明确将“无明显延迟”作为自动激活的前提。[W3C：Tabs Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)

但普通跨页面链接不因外观像标签，就必须使用 tab 语义。最终走查应包含鼠标、键盘、刷新、直接链接和返回五条路径：任一条让用户不知道自己在哪，问题就不只是配色。下一期进入表单：怎样让用户少填错，而不是出错后再堆提示。

## 今日实践

选一个测试环境中的文档任务，分别记录三类信息：下一次模型调用必须知道的事实、流程恢复必须保存的状态、用户返回页面应恢复的筛选与位置。然后用虚构数据做三次检查：压缩上下文后是否仍记得一项关键限制；审核后修改草稿是否使旧审批失效；从直接链接进入详情后是否还能理解归属并回到列表。

这三个问题不应交给同一段聊天历史解决。精确事实要能追溯，执行结果要有业务凭据，导航则应在刷新、返回和跨区域切换时保持一致。下一期 UI 连载进入表单设计，继续讨论如何减少输入错误。
