## 为什么会有 ChatBook？

在 LLM 还没有普及的时候，我的学习路径很固定：看视频教程，跟着 IDE 敲代码。学完一门课，再开下一门。但很快我意识到一个问题 —— **学完就忘**。那些花了好几个小时才啃下来的概念，过两周只剩一点模糊的印象。

后来我开始用写文章的方式巩固学习。把一个知识点用自己的话讲清楚，这个过程本身就是最好的复习。效果不错，但写一篇文章太慢了 —— 从整理思路、收集资料到成稿，一两个小时起步。

然后 LLM 来了，我的学习方式被彻底改变。以前是一个人啃视频、调试代码、搜 Stack Overflow，现在变成了**和 AI 对话 + AI 辅助编码**。我拥有了一群永远不会不耐烦的老师，不管问题多奇怪、多基础，它们都会认真回答。我的技术视野一下子被拉高了，学习速度也快了太多。

但新的问题出现了。

那种“原来如此”的顿悟瞬间，只在对话发生的当下存在。翻聊天记录翻不到那个感觉。GPT 的对话历史只是一串文本，它不会帮你还原当时的思考路径 —— 那些纠结、碰撞、层层剥开才得到的结论，被压缩成了一行行扁平的文字。

我需要一个工具，能把我和 AI 的讨论变成一篇文章。不是简单的“帮我写一篇关于 X 的文章”，而是把对话中真正有价值的东西萃取出来。

市面上有没有现成的方案？语雀需要超级会员，溪流也要会员。我要的东西很简单：一个在线平台，任何时候打开就在那里，对话、笔记、文章，都在一个地方。

那就自己搭一个。

## Agent 真的会记住我吗？

搭平台之前，我得先搞清楚 Agent 到底是什么。

当时的我对 Agent 的认知非常朴素：AI 是个万事通，有问题问它就行。它能跟我就一个话题聊好几轮，还能记住我之前说过什么 —— 这不就跟对面坐了个人一样吗？只是脾气更好，永远不会不耐烦。

甚至在一些 Agent 相关的视频里，有人说“所有 Agent 都病了，因为看过了人类的善与恶，它们抑郁了”。

我差点信了。

直到我打开 Spring AI 的源码。

你们知道我看到了什么吗？

**就是 CRUD。**

一个发送请求的请求头，一个会话历史列表。Agent 根据这个历史列表，计算下一个 token 应该是什么。仅此而已。它不会“记住”我。它只是在每次请求时，把之前的对话记录重新塞进 prompt 里。所谓的“记忆”，不过是上下文窗口内的文本拼接。聊天记录越长，前面的内容越容易被截断，Agent 就越“健忘”。

我盯着那段代码看了很久。有点幻灭，但更多的是释然 —— **Agent 没有记忆，记忆是设计者赋予它的结构。** 如果我希望它“记住”什么东西，我必须自己设计一个记忆模块。

## 当文字变成代码的入口

继续往下挖源码的时候，我看到了更精妙的设计。

Agent 每轮回复之后，设计者会对返回的内容做一次拦截。他会检查消息里有没有一个叫 `tool_call` 的标记。如果有，就根据这个标记找到对应的函数，执行它，把结果拼回去，再让 Agent 继续回复。循环往复，直到回复里不再出现 `tool_call` 为止。

这是个醍醐灌顶的时刻。

**模型吐出来的文字本身没有意义。有意义的是那个在关键时刻截获标志性文字的动作。** 这个拦截，让一段文本变成了代码的入口 —— 函数被调用了，数据库被查询了，外部 API 被请求了。从一串无意义的字符，变成了规则、变成了数据、变成了对真实世界的操作。

Agent 从此有了手和脚。

这个认知成了我后续设计的底层逻辑：**我们不是在写“智能”，我们是在定义文字何时、如何触发行动。**

---

## 第一次尝试：给我来了一坨大的

了解了 Agent 的基本原理后，我信心满满地让它直接生成文章。

结果？一坨大的。

那些文本没有任何价值 —— 正确的废话，空洞的总结，毫无洞察力。读完之后不会对任何事有新的理解。它只是把你可能想听的话套上一个“文章”的格式。

但我没有失望。因为我的目的本来就不是“让 AI 凭空写文章”。我知道 AI 凭空编不出好东西 —— 它没有真实的经验，没有在某个问题上纠结过，没有经历那个“搞不懂 → 反复试 → 终于通了”的过程。

我真正想要的是：**让它把我和它的讨论过程，变成一篇文章。** 讨论里那些碰撞、纠结、层层剥开才得到的结论，那才是文章的灵魂。AI 要做的不是创造，是萃取。

但第一版的结果告诉我：把聊天记录直接丢给 AI，它只会做一个低水平的摘要 —— 我问了什么，它答了什么，然后就没有然后了。真正在讨论中产生的核心洞察，一个字都没抓住。

---

## 链路编排的陷阱

我开始反思自己的设计。结论是：系统复杂度不够。AI 的意图不够清晰。没有 RAG。没有流程。

于是我设计了一套自以为很完整的链路编排：

```text
用户输入
  → 轻度意图判断（是不是该进入 Agent 处理？）
  → 拦截器链（规则 / 权限 / 降级）
  → 意图分析（丢给 LLM 判断用户到底想干嘛）
  → Analysis View 选择 + Context 构建
  → Task 路由
  → Task Tool 执行（Service 调用 / SQL 查询）
  → 结果聚合
  → LLM 总结表达
```

八个步骤。每一步都有对应的类和配置。我越写越多，越写越重，最后所有 Agent 请求打到同一家模型平台，直接触发限流。

卡在这里卡了很久。

然后某天在 GitHub 上搜 Claude Code 相关的代码仓库时，无意中翻到一个项目 —— `learn-claude-code`。项目里有一篇文章，标题我不记得了，但有句话打在我脑门上：

> **“你不是在编写智能，你是在构建智能栖居的世界。”**

我在干什么？我在往一条流水线上堆步骤。我在用微服务那套思路 —— 拦截器、路由、聚合 —— 去解决一个本质上不是编排的问题。

那句话之后我彻底放弃了那个八步流水线。开始重新想：我到底需要一个什么样的“世界”，让 Agent 能在里面把一件事做好？

## 笔记本：给 Agent 一个“外部记忆”

我重新审视了自己的使用场景。

我跟 AI 对话主要干什么？**讨论一个话题，然后学习相关的知识。** 不是一步到位的“帮我写文章”，而是一个逐渐深入的过程：抛出一个想法 → 讨论可行性 → 补充背景知识 → 梳理结构和论点 → 积累足够的素材 → 才开始成稿。

如果这是一个人的工作流，他会怎么做？他会拿一个笔记本，把讨论中的重点随手记下来。写到一定程度，翻翻笔记，觉得差不多了，开始写初稿。写完再改。

于是我把这个“笔记本”做成了 Agent 运行环境的核心组件：

```java
NotebookSummary {
    goal,               // 写作目标
    currentScene,       // 当前在哪个阶段
    userIntent,         // 用户意图
    facts[],            // 已确认的事实
    knowledgePoints[],  // 积累的知识点
    openQuestions[],    // 待解决的问题
    outline[],          // 大纲
    styleRules[],       // 风格约束
    editingTargets[],   // 编辑目标
    draftReadiness,     // 是否具备成稿条件
    nextSuggestedAction // 下一步建议动作
}
```

这个设计有几个关键点：

1. **笔记本不是聊天记录。** 聊天记录是扁平的、时序的、混着大量废话和试探的。笔记本是结构化提取 —— 只保留事实、知识点、待解决问题、大纲条目。每轮对话结束后，后台自动跑一个 `NotebookSummarizeTask`，让 AI 帮用户更新笔记：新增了什么事实？解决了哪个问题？大纲需要调整吗？
2. **笔记本有自我评估能力。** `draftReadiness` 是一个启发式指标：`facts ≥ 3` 条，`outline ≥ 2` 条，`openQuestions ≤ 1` 条 → `READY`。这个判断不靠 LLM（太慢，还需要额外请求），而是直接数笔记本里的条目。当用户提到“帮我生成初稿”时，Agent 会先看看笔记本 —— 准备好了就建议生成，没准备好就告诉用户还需要补充什么。
3. **笔记本跨场景流转。** 讨论场景攒下来的笔记，到了初稿生成场景直接作为输入。生成完了，笔记本更新状态，自动进入编辑场景。场景切换不丢上下文。

这就是我说的“栖居的世界” —— 不是设计一条精密的流水线，而是设计一个结构清晰的环境，让 Agent 在这个环境里知道：**我在哪？我知道什么？我还缺什么？下一步该干什么？**

## 场景路由：不是所有的对话都一样

有了笔记本，下一个问题是：Agent 怎么知道当前该用哪种方式回复？

不是所有的对话都该被同等对待：
- 用户问“这个原理是什么” → 应该进入学习模式，拆解概念、举例、对比；
- 用户说“我想讨论一下这个方向” → 应该进入讨论模式，扩展视角、补充反方观点、追问；
- 用户说“帮我把这段话润色一下” → 应该进入编辑模式，关注措辞、结构、风格；
- 用户说“可以生成初稿了” → 应该进入草稿模式，基于笔记本组织成文。

于是有了 `AgentSceneRouter` —— 一个纯规则引擎，不做 LLM 调用：

```text
用户消息 → 关键词匹配 →
  ├─ 编辑关键词 + 有草稿上下文 → EDIT
  ├─ 草稿关键词 + 笔记本就绪 → DRAFT
  ├─ 草稿关键词 + 笔记本不足 → DISCUSS/LEARN（继续收集信息）
  ├─ 学习关键词 → LEARN
  ├─ 讨论关键词 → DISCUSS
  └─ 默认 → 继承上一轮场景状态
```

**用规则引擎而不是 LLM，有两个原因：延迟和成本。** 场景判断在每次用户消息发送前就要完成，如果每次判断都调一次 LLM，首字延迟直接爆炸。而写作场景的关键词分布非常稳定 —— 说“润色”“改写”就是想编辑，说“原理”“解释”就是想学习。规则匹配在这个上下文里准确率足够。

但这套路由真正有意思的地方不是关键词匹配本身，而是 `currentScene` 和 `nextScene` 的分离。

当前轮用什么场景回复，和下一轮建议切换到什么场景，是两个独立的决策。比如用户说“生成初稿”，但笔记本还没就绪 —— 当前场景仍然是 `DISCUSS`（继续帮用户理清思路），但 `nextScene` 指向 `DRAFT`（告诉前端“接下来你可能想生成草稿了”）。前端根据这个信息，在 UI 上显示不同的提示和按钮。

场景决策不是一次性拍板的。每轮对话结束后，笔记本被刷新，`finalizeDecision()` 重新评估准备度，场景可以在**讨论 → 学习 → 草稿 → 编辑**之间平滑漂移。

## 流式输出：让一句话边想边显示

传统的聊天是同步的 —— Agent 想完一整段，一次性返回。这在讨论场景下体验很差：你发了一句话，等 5 秒钟，然后一大段文字突然出现。

但直接让 AI 流式输出原始文本也不行。因为 Agent 返回的不只是给用户看的文字，还有结构化的元数据 —— 消息类型是 `text` 还是 `interactive_form`？如果是表单，有哪些问题和选项？

我需要一种格式，能同时承载流式预览和结构化最终结果。

最终的设计是**双片段输出**。每个 prompt 模板都要求 AI 按固定格式回复：

```xml
<agent_preview>这段文字实时流式展示给用户看...</agent_preview>
<agent_final>{"messageType":"text","content":"...","payload":null}</agent_final>
```

或者对于交互式表单：

```xml
<agent_preview>为了帮你梳理文章结构，我需要了解几个信息：</agent_preview>
<agent_final>{"messageType":"interactive_form","content":"简短引导语","payload":{...表单结构...}}</agent_final>
```

后端流式处理时的逻辑（`AgentConversationServiceImpl.handleStreamingChunk`）：
1. 从 `<agent_preview>` 标签中增量提取预览文本 → 通过 WebSocket 推送给前端；
2. 如果 preview 标签还没出现，尝试从部分 JSON 的 `content` 字段提取预览 → fallback；
3. 如果连 JSON 都还没开始，直接裸文本推给前端 → 第二层 fallback；
4. 流完成后，从完整的 `<agent_final>` 中解析出结构化消息 → 存入数据库。

这套设计的好处是：**流式预览和持久化结构互不干扰。** 预览只管“让用户尽快看到文字在增长”，最终消息只管“数据结构完整、可查询、可复现”。两者通过 prompt 约束耦合在一起，但在代码层面完全解耦。

还有一个细节：`reconcileAssistantMessage()` 处理了预览和最终消息不一致的情况。如果 final content 解析出来是空的，就用 preview 文本补上；如果 preview 比 final 更长，就用 preview（因为流式输出时 AI 可能给了比最终 JSON 更自然的表达）。这些边界情况在实际运行中都出现过。

## 两种 Provider，一套接口

AI 领域变化太快了。今天用 Claude，明天可能切 DeepSeek，后天可能用自己的部署。我不能把代码绑死在某一家的 SDK 上。

设计上分了两层抽象：

- **第一层 —— `ArticleAiExecutionEngine`**：负责“调用哪家的 AI”。目前有两个实现，`AnthropicArticleAiExecutionEngine` 和 `CodexArticleAiExecutionEngine`，通过配置文件里的 `agent.ai.provider` 切换，启动时自动注入对应的 Bean。
- **第二层 —— `ArticleAiTask<T>`**：负责“这次调用做什么”。每个场景对应一个 Task 策略，Task 自己决定选哪个模型、用哪个 prompt 模板、怎么解析响应。目前有 8 个 Task：
  - `ArticleChatTask` — 讨论场景
  - `ArticleLearnTask` — 学习场景
  - `ArticleEditChatTask` — 编辑场景
  - `ArticleDraftGenerateTask` — 生成初稿
  - `ArticleDraftOptimizeTask` — 优化草稿
  - `ArticleSummaryExtractTask` — 提取摘要
  - `NotebookSummarizeTask` — 后台自动刷新笔记本
  - `ArticleEditorAssistTask` — 编辑器内 AI 辅助

两层独立变化：换 AI 厂商不影响任何 Task，新增一个场景也不影响执行引擎。

这个架构的灵感直接来自当初读 Spring AI 源码时看到的 Tool 拦截机制 —— 在这个设计中，`ExecutionEngine` 相当于“调用 AI 的手”，`Task` 相当于“组织任务的脑”。一个负责怎么请求，一个负责请求什么。

## MCP：把 Agent 的能力暴露出去

ChatBook 最初只是一个 Web 应用 —— 用户在浏览器里打开 Agent Studio，跟 AI 对话，生成文章。

但另一个使用场景浮现了：我在 Claude Code 里跟 AI 讨论技术问题，聊透了之后想直接生成一篇文章草稿。难道我还要把对话内容复制粘贴到 ChatBook 里？太蠢了。

MCP（Model Context Protocol）解决了这个问题。我写了一个独立的 Node.js 服务 —— `chat-book-mcp-server` —— 把“创建文章草稿”包装成一个 MCP Tool：

```text
Claude Code / Cursor / 其他 AI 编程工具
    │ MCP Protocol
    ▼
chat-book-mcp-server
    │ 校验输入 → 敏感内容扫描 → 调用 ChatBook API
    ▼
ChatBook 平台（草稿入库）
```

这个 MCP Server 很小，核心就两个文件：一个 `server.ts` 启动服务（支持 stdio 和 HTTP 两种传输方式），一个 `createArticleDraft.ts` 定义工具逻辑。

有意思的是**敏感内容扫描**这一步。MCP Server 接收的是外部 AI 工具产生的 Markdown 内容 —— 我们没办法控制那个 AI 的输出质量，甚至没办法预判它会夹带什么东西。所以在入库之前，`sensitiveScanner` 会对标题、摘要、正文做一次正则扫描，检查是否包含 API Key、数据库连接串、私钥等敏感信息。扫描到就拒绝，不会入库。

这其实是前面那个认知的延伸 —— **拦截文字，让文字触发行动。** 只不过这次拦截不是为了执行，而是为了阻止。

## 总结

从“Agent 有记忆吗”这个朴素的问题出发，到最后搭建出一个能跑的多场景写作平台，这个过程比我预想的要长得多。

如果要提炼几个真正有用的结论：

1. **第一，Agent 不会记住你。记忆是你设计出来的。** Notebook 不是可有可无的 feature，它是 Agent 能跨轮次、跨场景工作的基础。没有结构化记忆的 Agent，本质上就是一个“一次性问答机”。
2. **第二，场景不是 prompt 里的角色扮演，而是 笔记本内容 + prompt 模板 + 执行策略 的组合。** `SceneRouter` 负责判断该进入哪个场景，`Task` 负责在那个场景下正确执行。场景切换的核心不是“换提示词”，而是“换上下文结构”。
3. **第三，代码最有价值的部分往往在“拦截”的地方。** Tool call 的拦截让函数活了过来；`<agent_preview>` 的提取让流式展示成为可能；MCP 的敏感扫描让安全从口头承诺变成了代码行为。最精妙的设计不在核心流程里，在边界上。
4. **第四，也是在那个 GitHub 仓库里读到的那句话：你不是在编写智能，你是在构建智能栖居的世界。** 好的 Agent 设计不是往流水线上堆步骤，而是给 Agent 一个有结构的环境 —— 它知道自己在哪、知道什么、缺什么、下一步该往哪走。其余的事，模型自己会搞定。
