## 1 AI与软件工程新闻

过去一天，两项值得分开理解的新进展，都在把 AI 接进已有工作流：一项让聊天连接企业工单与业务动作，另一项让开发环境直接调用图像工具。它们的共同点是减少切换，却不能据此推导出“基础模型全面变强”。以下日期均按原文，本期于北京时间 10 月 29 日晨间核验。

**10 月 28 日，OpenAI 与 ServiceNow 扩大合作，但“今天可用”和“明年计划”有清楚分界。** 公告确认，ServiceNow MCP 插件当天已在 OpenAI marketplace 提供；客户连接自己的 ServiceNow 实例，并选择开放哪些能力，Action Fabric 沿用企业已有业务规则和权限。因而，值得关注的不是聊天框变成万能管理员，而是业务上下文与受权限约束的动作开始进入同一入口。公告还展示了在 ChatGPT 内查看告警、近期变更、受影响服务并分派处理团队的交互体验，但这部分是预览。增强能力预计年底前推出；Codex 接入 AI Workflow Factory 则预计在 2027 年，不能写成今天已经可以用 Codex 自动交付 ServiceNow 应用。[OpenAI 官方公告](https://openai.com/index/openai-servicenow-partnership-expansion/)

这对软件团队的实际启示是：连接器解决“能接到什么”，权限与记录解决“能做什么、由谁负责”。如果以后评估这类产品，先让它读取一张测试工单、解释关联关系，再检查写入动作能否被现有审批与审计约束，比观看一次端到端演示更能说明适用性。这里是评估方法，不是对公告中尚未上线功能的实测结论。

**同日，GitHub Copilot 的图像生成与编辑进入公开预览。** 用户在聊天中提出图像需求，所选推理模型调用独立的 **GPT Image 2.5 Flare** 图像工具，随后内联预览并把结果保存到项目。也就是说，“Copilot 会生图”是产品编排，不等于当前选中的代码模型原生输出了图像。该预览面向 Pro、Pro+、Business 和 Enterprise，可在 VS Code、Copilot app 与 CLI 中使用；图像 token 与聊天模型分开计费，并消耗方案的 AI credits。组织管理员可禁用图像模型，可见的 “Made with AI” 水印则是可选、默认关闭。[GitHub 图像功能公告](https://github.blog/changelog/2026-10-28-generate-and-edit-images-directly-in-copilot/)

对设计协作而言，价值是让占位图、界面概念和代码留在同一项目语境里；代价是素材更容易“生成后直接混入交付”。因此应把草稿资产与正式资产分开，并在发布前核对品牌、文字、授权和 AI 标识要求。水印默认关闭只是产品设置，不代表图像不需要披露，也不替代团队自己的素材审查。

## 2 模型特性与本地路由

理解MAI Code 1.1 Flash的本地化变化，最好先画清三个层次：**模型负责生成与推理，路由系统决定使用哪个模型，执行环境决定工具实际能做什么。** 微软在 **10 月 7 日**的本地化更新中已经介绍 MAI Code 1.1 Flash 的本地版本；**10 月 28 日**的新变化，是 Copilot Fusion 开始提供本地与云端之间的自动路由实验预览，不是同一天重新发布了一个基础模型。[本地路由发布说明](https://github.blog/changelog/2026-10-28-github-copilot-fusion-now-supports-selection-of-local-models/)

Fusion 本身已正式可用，但它不是一个模型名字。用户选择 Standard、High 或 Max 来表达投入偏好，系统可以让一个模型直接完成任务，也可以先由经济型模型起草、检查后再升级，或由另一模型审阅后交回修改。这是把任务分工与质量检查做成产品，而不是把多个模型的参数合并；计费仍按实际调用模型计算，不能因为选了“自动”就假定每次更便宜。尤其要把 **Fusion 正式可用**与**本地路由仍属实验预览**分开。[Fusion 发布说明](https://github.blog/changelog/2026-10-28-route-and-orchestrate-models-with-github-copilot-fusion/)

MAI Code 1.1 Flash 在这里提供的是面向编码工作的本地计算选项。本地版通过量化降低模型存储负担，并采用推测解码：草稿模型先提出候选 token，目标模型验证，而不是无条件采纳较小模型的猜测。官方工程文章列出的量化体积为 53GB；在指定 Surface Laptop Ultra 测试机上，256k 上下文时峰值内存达到 75.5GB。两个数字的差距提醒我们：**装得下权重，不等于跑得稳完整任务**；上下文缓存、运行时和其他应用仍要占用内存。这些是厂商指定环境的数据，不是任意电脑的实测保证。[微软 10 月 7 日工程说明](https://commandline.microsoft.com/local-models-sandboxed-tools-github-windows/)

实际安装门槛也不能用“本地小模型”一笔带过。当前官方 CLI 文档列出的托管下载条件是 Windows、NVIDIA GPU（不支持 AMD），至少 **96GB 可用 combined RAM**和 **60GB 可用存储**；还要求兼容的 llama.cpp 运行时与路径设置，并启用实验功能。这里保留文档的 combined RAM 口径，不把它擅自换算成普通电脑的内存条容量。多种 Copilot 客户端同时加载各自的模型实例还可能耗尽内存，因此不是下载一次就适合到处并行运行。[GitHub CLI 安装条件](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-llm-models)

最后，**自动选中本地模型不等于会话离线**：10 月 28 日说明明确表示，Fusion 的路由决策仍在云端。本地模型可能有不同于云端模型的安全保护；工具权限也不会因推理搬到设备上就自动收紧。因此，它更适合有合格硬件、重复编码工作量，并愿意测量完成率与总成本的团队试验；若目标是严格网络隔离，必须另行核对离线配置、模型端点和工具网络权限，而不能把“本地路由”当作数据不离机的保证。今天的判断标准仍是完整任务的结果：相同测试能否通过、失败后如何回退、记录是否可追溯，而不是仅比较每秒输出多少 token。[路由边界](https://github.blog/changelog/2026-10-28-github-copilot-fusion-now-supports-selection-of-local-models/)、[离线配置文档](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-llm-models)


## 3 模型配置与异步批处理

本章沿用虚构场景：客服团队有 100 条已脱敏的工单，需要在次日汇总前得到摘要，而不是让在线客户等待。这里的“异步”不是把一个同步请求藏进后台线程，而是先把请求集合交给供应商，拿到批次凭证，稍后查询并领取结果。教学对象是 **Anthropic Claude API 的 Message Batches API，`/v1/messages/batches`，显式版本头 `anthropic-version: 2026-10-21`**。文档核验日为 **2026-10-28 UTC**；以下请求、结果数量和故障均为教学示意，**未调用 API、未实测**。API 版本与模型版本应分别记录。[版本说明](https://platform.claude.com/docs/en/api/versioning)

为什么值得使用？当 100 份输入彼此独立、允许稍后交付时，批处理能把“立即响应”换成成本空间；当前官方说明按标准 API 价格的 50% 计费。它不适合实时客服回复，也不适合下一项必须读到上一项结果才开始的链条。容量边界是每批最多 100,000 个请求或 256 MB，先到者为限；处理窗口为 24 小时，仍未处理的请求会过期。结果下载期从批次**创建**起算 29 天，不是从完成起算。“多数在一小时内完成”不能变成你向业务承诺的一小时 SLA。[批处理指南](https://platform.claude.com/docs/en/build-with-claude/batch-processing)

输入不是一个“总结全部工单”的大提示，而是 `requests` 数组：每条有批内唯一的 `custom_id` 和独立的 `params`。标识可用 1 至 64 个字母、数字、连字符或下划线；不要塞进姓名、邮箱。下面只展开第 1 条，其余 99 条采用相同结构，但各有标识和工单内容；`max_tokens` 是单项生成 token 的总上限，不是全批共享额度。[创建接口](https://platform.claude.com/docs/en/api/messages/batches/create)

```json
{
  "requests": [{
    "custom_id": "daily7-ticket-001-a1",
    "params": {
      "model": "claude-sonnet-5-5",
      "max_tokens": 4096,
      "messages": [{
        "role": "user",
        "content": "把以下虚构工单概括为问题、已做处理、待办三句；没有的信息写未知。工单：用户收到错色商品；客服已核对订单，待仓库确认换货。"
      }]
    }
  }]
}
```

每个 `params` 都应包含完成本条任务需要的上下文。比如第 87 条不能只写“按第一条的要求总结”，因为批次不是一段共享对话。把摘要规则复制到各自请求中，输入仍是一条工单，输出仍对应一条工单。这样某项失败时，才有办法单独定位和修复，而不必重建一整段隐含的依赖关系。

这条虚构工单的合格业务输出可以是：“问题：收到错色商品。已做处理：客服已核对订单。待办：等待仓库确认换货。”它不是本次实际生成结果，而是事先给验收者看的目标样例。

示例模型 ID 在当日官方模型表中列为 Claude Sonnet 5.5；这里用于展示请求形状，并不表示已完成模型选型或质量测试。该型号默认启用 adaptive thinking，思考 token 也占用 `max_tokens`；4096 是本例的示意总预算，不保证得到4096个可见正文 token，也不是推荐用量。领取结果后仍要检查 `stop_reason` 与内容是否完整，不能把供应商请求成功当作摘要已经合格。[Sonnet 5.5说明](https://platform.claude.com/docs/en/models/sonnet-5-5/overview)、[模型表](https://platform.claude.com/docs/en/models/overview)

提交 `POST /v1/messages/batches` 后，首先得到的是批次对象，不是 100 份摘要。保存它的 `id`，再以 `GET /v1/messages/batches/{id}` 查询；这个读取接口可用于轮询。不能因为 HTTP 请求结束，就把业务任务标为完成。[查询接口](https://platform.claude.com/docs/en/api/messages/batches/retrieve)

尤其要注意：按字段说明，`request_counts.processing` 是处理状态中的请求数，而成功、出错、取消、过期四种计数在整批结束前为零。但当前文档的响应示例与字段说明存在不一致；本课保守地不据此推算实时完成率，实际接入需在目标版本核验。界面先显示“供应商处理中”，等批次到 `ended`，再核对最终计数。[批次类型定义](https://platform.claude.com/docs/en/api/http/messages/batches)、[查询响应示例](https://platform.claude.com/docs/en/api/messages/batches/retrieve)

领取结果使用对象里的 `results_url`，或 `GET /v1/messages/batches/{id}/results`。返回 JSONL：一行一个单项结果，但顺序没有保证，必须用 `custom_id` 找回原工单，不能把第 1 行强配给第 1 条输入。[结果接口](https://platform.claude.com/docs/en/api/messages/batches/results) 单项分为 `succeeded`、`errored`、`canceled`、`expired`：成功项带 `message`，错误项带错误信息，另两类说明没有得到该项输出。[结果类型](https://platform.claude.com/docs/en/api/http/messages/batches)

假设最后是 94 项成功、4 项出错、2 项过期，批次可以已经 `ended`，但你只有 94 份待验收摘要。**练习：** 若结果第一行属于 `daily7-ticket-087-a1`，该写入哪条工单？若整批结束后只读入 99 行，能宣布完成吗？答案是按标识写入第 87 条，并继续查找缺失项或读取故障。还要核对“收到的标识集合”和“提交的标识集合”相同，而不只是数够 100 行：一个重复标识加一个遗漏项，也可能凑出 100 行；“结束”不是“全成功”，读到文件尾也不自动证明业务收齐。

## 4 架构设计与后台恢复

上一章解决“怎么交给供应商”；这一章解决“我们的系统怎么知道交到哪里了”。以下是依据接口语义提出的**应用架构建议**，不是 Anthropic 提供的额外保证。只要任务可能跨越进程重启、部署或人员交接，就值得做；一次性的人工演示可以简化，但凡要承诺交付，就不能只把批次 ID 放在内存变量里。

先把三层身份分开。**业务任务**表示“给今天 100 条工单生成摘要”，记录总目标与验收规则；**供应商批次**记录某一次提交得到的批次 ID、供应商状态和结果位置；**单项任务及尝试**记录哪条工单在第几次尝试中被交给哪个批次、用了哪个 `custom_id`。一个业务任务可能拆成几个批次，也可能只为失败项新增批次，不能用一个 `status` 字段兼任三层状态。输入是 100 个稳定工单 ID、各自的内容版本与摘要规则；最终输出应是 100 条可追溯的验收记录，或明确列出尚未交付的项目。

建议把业务任务走成 `prepared → running → collecting → completed`，另设 `partial_failed` 和 `submission_unknown`。这些名称由应用自定义；本例只有100项都满足交付要求才记为 `completed`，部分项目未交付就明确保留缺口。供应商仍使用它自己的 `in_progress`、`canceling`、`ended`；不要把两套状态硬映射。取消也不是回滚：官方指出取消过程中仍可能完成已在执行、不可中断的请求，因而取消后也要收集已有结果。[取消接口](https://platform.claude.com/docs/en/api/messages/batches/cancel)

提交前，先持久化输入清单、内容哈希、提示版本、模型 ID、API 版本及各项标识；这些是之后对账的依据。提交成功后立刻保存供应商批次 ID。后台工作器只推进持久化记录，页面刷新只读取记录，不能重新触发提交。输入清单一旦提交就不要原地改写；如果客服随后修改了工单，应创建新内容版本，把旧摘要标记为针对旧版本，而不是让审计记录看起来像模型处理了它从未见过的新文本。为避免两个工作器同时领取同一项，应有明确的领取与互斥机制；但本地锁不能替供应商证明“刚才的提交没有发生”。

恢复必须按证据分支。**已有批次 ID**：重启后继续调用读取接口，处理中就继续等待，结束后转入结果采集；读取该批次不会创建新批次。[查询接口](https://platform.claude.com/docs/en/api/messages/batches/retrieve) **没有 ID、提交响应又丢失**：标记“提交结果未知”，查本地提交记录与同一 Workspace 的批次列表，必要时核对已完成批次的逐项标识。列表只提供候选，不保证凭时间和数量就能唯一认领一个批次；仍无法确认时应阻止自动补发并交给人工判断。不要把“本地不知道”翻译成“远端没做”。[列出批次](https://platform.claude.com/docs/en/api/messages/batches/list)

结果采集也要能恢复。以“供应商批次 ID 加 `custom_id`”做接收记录的唯一键，先保存该行及验收状态，再更新业务统计。若在第 57 行后重启，可重新读取结果，让已入库记录被识别为重复，而不是再生成 57 份摘要。这里的目标是让自己的落库不重复，不声称供应商恰好执行一次。若同一键出现矛盾内容，应隔离告警，不能静默覆盖。验收完成后，先确认结果对应的内容版本与尝试仍然有效，再以稳定业务键发布摘要；旧批次结果可以留档，但不得覆盖较新的有效结果。这样才能把“模型已经返回”和“业务已经可用”分开。比如输出成功却遗漏“待办”，应保留供应商的成功事实，同时把应用验收记为未通过，不要篡改供应商状态。重启恢复依赖的是这些已持久化事实，而不是重新运行一遍提示词来猜测旧结果。应用也应安排结果领取与归档，不能把供应商下载地址当永久备份；本地仍需遵守自己的访问控制和保存期限。

回到 94、4、2 的例子：先保存并验收 94 项；4 个错误按具体原因修复，2 个过期项按当前需求决定是否补做，新增尝试必须关联原单项。不要因一个坏项重发全部 100 条。假设这 94 份也全部通过验收并发布，且其余暂不补做，业务输出应写“94 份已交付，6 项未交付”，而不是把供应商 `ended` 改名为“全部成功”。**练习：** 重启时批次已结束，但本地只收了 57 行，下一步是重发 100 条还是读取旧结果？选择后者；只有完成单项对账，才能决定究竟还缺哪些工作。


## 5 大厂UI设计

**本期学习目标：让后台任务的变化被感知，同时保住用户正在操作的位置。** 上期讲空、错、加载分别表达什么，这次进一步处理“消息出现了，键盘用户怎么知道”。沿用本期的虚构任务：一次为100条客服记录生成摘要，用户提交后还要继续筛选、查看其他批次。

### 提交成功不必把人带走

键盘焦点决定下一次按键作用于哪里；状态公告则让辅助技术获知变化。两者可以分开。用户按下“生成100条摘要”后，本文建议保留当前操作上下文，在持久任务区显示“已提交，等待处理”，提供“查看此批次”。不要为展示成功就把焦点推到进度条，也不要删除当前控件，让焦点无处可去。

这有明确依据：[WCAG 2.2的4.1.3（AA级）](https://www.w3.org/TR/WCAG22/#status-messages)要求符合定义的状态消息可由程序识别，使辅助技术无需让消息获焦也能呈现它；它没有规定每次提交都必须移焦。[2.4.3（A级）](https://www.w3.org/TR/WCAG22/#focus-order)要求焦点顺序保留含义与可操作性。“留在原处”是本例的设计选择，不是所有页面的唯一答案：如果用户主动进入任务详情，或必须处理阻断操作的问题，就应设计明确的新焦点位置。

### 进度要能听见 但不要逐条抢话

Live region是允许辅助技术获知内容更新的区域。本例把简短摘要放进`role="status"`，不把整张100行结果表设为公告区。[WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/#status)规定该角色隐含`aria-live="polite"`与`aria-atomic="true"`：一般状态以礼貌优先级呈现，更新按完整信息理解，而非只听见一个脱离语境的数字。

本例在执行期间只显示“处理中，可以继续浏览其他批次”，不编造实时完成数量。轮询多次仍是同一状态，不必重复公告；短时间出现多个中间状态时，合并后只报最新变化，例如设置10秒的普通公告限速窗口。结束后另报“批次处理结束，94条请求成功，4条错误，2条过期”，不让最终结果被节流遗漏。请求成功还须经过摘要质量等业务验收，不能提前写成“94条已交付”。这个窗口是待测试的教学参数，**不是WCAG规定**。[WAI的解释文档](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)明确提醒过多公告会让应用过于吵闹。

还要检查组件默认值。[Fluent 2的Toast指南](https://fluent2.microsoft.design/components/web/react/core/toast/usage)说明，除info外的反馈态使用assertive，会打断其他读屏公告。因此，不能照搬成功Toast，给每条摘要都报一次成功。Toast适合短暂提示，必要操作不应只藏在那里；本例的未成功数量和查看入口持续保留在任务区。

### 查看失败项之后 还要能回来

用户主动按下“查看6条未成功项”，再把焦点带到详情，才符合他的意图。详情应把错误与过期分开，不能因为两者都没拿到摘要，就许诺相同的修复方法。若采用模态详情，可先聚焦“6条未成功记录”标题，随后按结构阅读原因与可用操作，避免一打开就落到“全部重试”。关闭时回到原入口；若入口已消失，回到该批次仍存在的合理位置，而非页面顶端。[WAI APG模态对话框模式](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)提供这种进入与返回焦点的指导，它是实现模式，不是另一条WCAG成功准则。

取消也别一律弹确认框。本文建议先核对真实后果：可恢复、代价很小的操作，说明影响后可考虑直接执行；若会丢弃不可恢复内容，再要求确认。确认框应写明具体损失，按钮直说将采取的动作，初始焦点可放在较安全的选择。不能用一个含糊的“确定”，把理解后果的责任交给用户。请求取消后仍须核对最终逐项结果，不能把“已请求取消”说成“100条全部取消”。

### 用一条完整路径验收

下面是待执行的走查脚本，不是已完成的测试报告。先只用键盘，再配合目标浏览器与屏幕阅读器复查：

1. 用Tab到提交按钮并按Enter。检查提交后的焦点仍有可见位置，接着能按合理顺序到达“查看此批次”；特别复查按钮变为不可用或被替换时的表现。
2. 让任务运行，同时操作筛选。确认更新没有夺走焦点，相同轮询状态不反复播报，最终成功、错误与过期数量仍可获知。
3. 打开失败详情，用Tab、Shift+Tab、Esc走一遍。模态内焦点不跑到背景，关闭后回到入口；再验证入口消失的分支。
4. 走取消路径，核对按钮可用键盘操作、后果可读，且请求取消、取消中与最终逐项结果没有混为一谈。

## 今日小实验

不接真实API，也可以先检查这套流程有没有自相矛盾。准备100条虚构工单的输入清单，给每条固定标识；再准备一个乱序的模拟结果文件，包含94条成功、4条错误、2条过期。这里的数量只是练习数据。成功内容中可以故意放一条缺少待办说明的摘要，让“请求成功”与“业务验收通过”不再碰巧完全重合。

按三个场景走一遍。第一种，后台只记到结果第57行就重启；恢复后重新读取同一份结果，应得到100个唯一接收记录，而不是157个。第二种，把第88条结果暂时拿走；即使提供方状态写着ended，本地也要指出少了哪个标识，不得宣布全部收齐。第三种，用户正用键盘筛选其他批次时，这批任务结束；界面应以状态公告通知，不把焦点拉走，用户主动打开未成功项后才进入详情。

参考判断有三层。接收层核对100条输入是否都有对应结果，重复与缺失分别记录；业务层核对摘要是否达到既定要求：若94条成功请求里只有那条缺少待办的摘要不合格，其余93条均通过并交付，就应显示“93条已交付、1条验收未通过、4条请求错误、2条过期”，同时保留供应商94条succeeded的原始事实。待处理入口还应包含那条验收未通过的摘要，不能只显示6条接口未成功项；交互层核对用户能否在不丢失当前位置的情况下发现问题、查看原因并返回。如果只修复失败项，应为新尝试保留与原项的关联，而不是删掉旧记录，假装从未失败过。这是本刊自拟练习，并非供应商认证测试，也不是已经完成的执行报告。

## 今天记住这四点

- 产品连接器、路由与图像工具的升级，需要与基础模型能力分开理解；本地推理也未必意味着会话离线。
- 异步批次先返回凭证，领取结果后按custom_id逐项对齐；ended不能代替全成功或业务验收。
- 让业务任务、供应商批次与单项尝试分别留存，重启后才能恢复读取、识别缺失，并避免未知状态下盲目重发。
- 状态公告可以让变化被感知，不必强行移动焦点；真实结果和下一步操作应保留在持久界面中。
